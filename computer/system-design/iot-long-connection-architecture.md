## 一、核心误区：统一入口 ≠ 单台机器

> **先破一个误区："统一入口"不等于"单台机器"。**
>
> 所谓统一入口，通常是一个 **VIP（虚拟 IP）或域名**，背后是一整层可水平扩展的 LB 集群。

真正的入口是"逻辑上统一"的：客户端只看到一个地址，但这个地址背后没有任何一台机器独占它，而是 **LB 集群 + 每台网关的 lo:0 网卡上绑着同一个 VIP**，大家一起冒充这一个入口。

## 二、分层架构总览：每一层负责什么

```
                    ┌─ 用户设备 (亿级终端)
                    │
                    ▼
         ┌─── DNS / GeoDNS / Anycast (就近接入) ───┐
         │              VIP: 1.2.3.4               │
         │                                        │
   ┌─────┴─────┐   ECMP / BGP   ┌─────────┐
   │ L4 负载均衡 │ ────────────→ │ L4 负载均衡 │   ← LVS / HAProxy tcp / F5 / NLB / 自研DPDK
   │  (多台,主备或双活)│             │  (多台)   │
   └─────┬─────┘                └────┬────┘
         │        (四层分发,只做转发,不解析协议)
         ▼
   ┌───────────────────────┐
   │   接入网关集群 (核心)    │   ← 这里才是真正"扛连接"的地方,10~20 台
   │  Nginx / Envoy / Go    │
   │  Netty / 自研 C 网关     │   每台扛 50万~100万 长连接
   └───────┬───────────────┘
           │  异步消息(不阻塞网关)
           ▼
   ┌───────────────────────┐
   │ 业务层: 消息队列 + 后端   │   ← Kafka/RocketMQ + 业务服务
   │ Redis: 设备在线状态/路由表 │
   └───────────────────────┘
```

**核心设计原则：连接网关（保活/收发）与业务处理完全解耦。**

- 网关只负责百万条 TCP 长连接的心跳和消息转发
- 业务逻辑全部异步丢给 MQ 处理
- 网关因此保持"无状态、纯转发"——这是能扛大规模连接的前提

## 三、连接归属：长连接到底建在哪一层

这是理解整个架构最关键的一张表。把每一层的"连接归属"说清楚，整个系统就通了：

```
域名 → 只是解析, 不建连接
 L4 LB(DR) → 不建连接, 只做 MAC 层转发
 网关 RS → 【真正持有长连接的地方】, 用 epoll 管几百万条
  业务后端 → 不持有连接, 通过 MQ 异步消费消息
```

| 层 | 是否持有连接 | 主要工作 | 单点能扛的量级 |
|------|------|------|------|
| DNS | 否 | 域名解析，粗分流 | 无连接压力 |
| L4 LB | 否（DR 模式） | 按规则转发数据包 | 单台几百万条会话表 |
| 接入网关 | **是** | epoll 管理长连接、心跳、收发 | 单台 100 万级 |
| 业务后端 | 否 | 异步消费 MQ、查 Redis | 由 QPS 决定 |

## 四、域名层：粗分流，只管"去哪个机房"

一个域名可以配多条 A 记录 / 多个 IP，靠 **DNS 轮询**或 **GeoDNS** 把不同用户解析到不同 VIP：

```
iot.example.com  →  202.x.x.1  (北京机房 VIP)
                 →  202.x.x.2  (上海机房 VIP)
                 →  202.x.x.3  (广州机房 VIP)
```

### 4.1 DNS 层的三个局限

| 局限 | 说明 |
|------|------|
| **粒度粗** | DNS 只知道"解析到哪个 IP"，不知道哪台服务器负载高 |
| **生效慢** | 客户端缓存 DNS（TTL 一般几十秒到几分钟），临时加机器不会立刻分流过去 |
| **只在建连时生效** | 连接一旦建立，后面所有数据包都跟 DNS 无关了 |

### 4.2 结论

> **DNS 负责"把流量分到不同机房/集群"，真正的精细负载均衡在 L4/L7 层做。**
>
> DNS 想控制到单机也行，但业界不会这么干——机器要动态扩缩容，DNS 跟不上。

## 五、L4 负载均衡：凭什么接得住百万长连接

关键要理解一件事：

> **L4 LB 不解析协议、不缓存、不做业务，它只做两件事——建立连接时登记一下，之后按规则转发数据包。而且长连接建立后大部分时间是"空转"的。**

### 5.1 它本身也是一组机器，不是单台

```
         VIP (1.2.3.4)
      ┌────┴─────┬──────────┐
   LB#1        LB#2       LB#3      ← 多台 L4 LB 组成集群
   (keepalived 抢 VIP / ECMP 分担)
```

- **Keepalived + VIP**：主备模式，一台持有 VIP，挂了漂移给备机
- **ECMP**：多个路由器把包 hash 到多台 LB，实现真正负载均衡

### 5.2 核心：连接空闲期"不干活"

一条长连接从建立到关闭的生命周期里，LB 的工作量分布：

| 阶段 | LB 做什么 | 消耗 |
|---|---|---|
| TCP 三次握手 | 参与建连（DR 模式干脆只转发 SYN） | CPU 一丁点 |
| **连接建立后（99% 的时间）** | **什么都不做，只维护一条会话记录** | **CPU ≈ 0，内存几百字节** |
| 有数据流动时 | 改 MAC/IP 头转发，不改数据内容 | CPU 极低，吃带宽 |
| 断开 | 删会话记录 | 一丁点 |

**关键点 1：长连接大多数时候是空闲的。** IoT 设备心跳一般 10 秒~60 秒才发一个小包，LB 在两次心跳之间对这条连接是零负担。

**关键点 2：LB 上每条连接只占一张很小的会话表项。** Linux conntrack 或 LVS 连接表里一条记录大约 **300~500 字节**：

```
100万 连接 × 400字节 ≈ 400 MB 内存
1000万 连接 × 400字节 ≈ 4 GB  内存
```

一台 64 GB 内存的 LB 机，纯内存角度放几千万条会话完全没压力（注意要把 `nf_conntrack_max` 调上去，默认才 6 万，这是很多人栽跟头的地方）。

### 5.3 高性能实现方式

| 方式 | 原理 | 性能 |
|------|------|------|
| **LVS** | 内核态转发，零拷贝 | 性能最好 |
| **DPDK** | 用户态网卡驱动，绕过内核协议栈 | 单机几百万~千万连接（大厂自研网关常用） |
| **HAProxy / Nginx tcp 模式** | 用户态四层代理 | 常用，够用 |

## 六、LVS 三种模式：NAT / DR / TUN

| 模式 | 原理 | 性能 | 适用 |
|---|---|---|---|
| **NAT** | LB 改包转发，所有出入流量都过它 | 一般，单台 10万级 | 中小规模 |
| **DR**（直连路由） | LB 只改 **MAC 地址**，后端网关直接回包给客户端，**回程不经过 LB** | 很高，单台轻松百万级 | 大厂主流 |
| **TUN**（隧道） | LB 封 IP 隧道发给后端 | 高 | 跨网段场景 |

**DR 模式最关键的点：请求进来经过 LB，响应直接由后端机器回给用户，不绕 LB。** 这样 LB 只扛"半程"流量，带宽压力减半，单台扛几百万连接很常见。

## 七、DR 直连模式：连接真的建在下面的网关上吗

> **对，DR 模式下，TCP 长连接确实直接建立在下面的网关（RS）上，LB 根本不持有这条连接。**

### 7.1 真实数据流

```
客户端 (设备)
  │  ① SYN, 目标 = VIP 1.2.3.4
  ▼
LVS LB
  │  ② LB 不做握手!只做一件事:
  │     按 hash 选一台网关(比如 RS2),
  │     把数据包的【目的MAC】改成 RS2 的 MAC, 原样转发
  ▼
RS2 网关  ← (lo:0 网卡上也绑了 VIP 1.2.3.4)
  │  ③ RS2 收到目标为 VIP 的 SYN
  │     自己完成三次握手, 持有这条连接
  ▼
客户端 ← ④ SYN-ACK 由 RS2 直接回给客户端, 不经过 LB
```

### 7.2 三个关键点

1. **LB 没有参与三次握手**。它就像一个快递中转站：只看"这个包裹该送去哪个仓库"（改 MAC 地址），包裹内容它碰都不碰。
2. **真正完成握手、持有连接的是 RS2 网关**。连接直接建到下面的网关上。
3. **客户端无感知**。它全程只知道自己在连 `1.2.3.4`（VIP），不知道 RS2 的存在。因为 RS2 的 loopback 上也绑了这个 VIP，所以它收包、回包都"冒充" VIP。

### 7.3 为什么这样设计反而更好？

因为 **LB 不持有连接 = LB 几乎没有连接成本**，这正是它扛得住百万级连接的原因：

| | 连接建在哪 | LB 上每条连接的成本 | LB 崩溃影响 |
|---|---|---|---|
| **DR 模式** | 在网关 RS 上 | 只记一条几百字节的转发表 | 极小：已建立的连接不受影响，只影响新连接 |
| **NAT 模式** | 在 LB 上（逻辑上） | 要维护源/目的地址转换表 | LB 挂 → 后面连接全断 |
| **L7 代理模式** | LB 上持一条 + 转发后另起一条 | 每条连接两个 socket、一堆状态 | LB 挂 → 全断 |

> DR 模式的 LB 是"打不死的转发器"：就算它重启，已建立的百万条连接一条都不会断（转发表重建一下，后续包继续按规则走）。

## 八、单机扛百万连接（C10M）

单台机器理论上能扛 **1~2 百万** TCP 连接。瓶颈不在 CPU，而在于 fd、内存和内核参数。

### 8.1 内核参数（必须调，默认值撑不住）

```bash
# /etc/sysctl.conf
fs.file-max = 40000000                 # 全局文件描述符上限
net.core.somaxconn = 65535             # accept 队列
net.ipv4.tcp_max_syn_backlog = 65535   # 半连接队列
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.ip_local_port_range = 1024 65535  # 本机发起连接的端口范围
net.ipv4.tcp_fin_timeout = 30
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_mem = 786432 1048576 1572864
# 如果用了 conntrack(NAT 场景):
net.netfilter.nf_conntrack_max = 20000000
```

进程级：`/etc/security/limits.conf` 里 `nofile` 要设到 `1048576`。

> **注意：10M 连接 = 每个节点要能开 100万 个 fd，这往往是第一个挂的点。**

### 8.2 连接的内存账（很重要）

每条 TCP 连接内核侧大约占 **2~4 KB**，加上应用层的读写缓冲区：

| 连接数 | 内核内存 | 应用缓冲(按 16KB/条) | 合计/台 |
|---|---|---|---|
| 100 万 | ~3 GB | ~16 GB | ~19 GB |

千万级连接不是一台机器的事，是几十台机器 + 内存大户。

**优化手段**：
- 连接不活跃时把缓冲区缩小（`SO_RCVBUF` 动态调整）
- 空闲超时踢掉僵尸连接

### 8.3 事件驱动模型（别用"一连接一线程"）

- **epoll / io_uring**（Linux）、**kqueue**（BSD）——单线程事件循环可以管 10 万+ 连接
- 用 **SO_REUSEPORT**：让多个 worker 进程/线程都 bind 同一个端口，内核帮你把 accept 请求分散到各核，避免 accept 锁竞争
- 典型实现：nginx `worker_processes = CPU核数` + `SO_REUSEPORT`；Go 的 goroutine 天然适配；Java 用 Netty；高性能自研用 C/Rust（tokio）

```nginx
# nginx 接入示例
worker_processes auto;
worker_rlimit_nofile 1048576;
events {
    use epoll;
    reuseport on;      # 多 worker 共享端口
    worker_connections 65535;  # 每 worker 6.5万 × 16 worker ≈ 100万
}
```

### 8.4 网卡侧

- 多队列网卡 + **RSS**（Receive Side Scaling），把中断分散到多核，`irqbalance` 或手动绑核
- 万兆/40G 网卡
- 千万级连接主要吃内存，但消息 QPS 高时带宽是瓶颈

## 九、从百万到千万：水平扩展 + 单元化

单机顶多 1~2 百万，千万级必须上集群，架构上要保证：

### 9.1 接入网关集群 = 纯水平扩展

- 网关**无状态**，加机器就能加容量 → 10~20 台 × 每台 100 万 = 千万级
- L4 LB 层做 `ip_hash` / 一致性哈希，把同一设备的连接固定到同一台网关
- 网关挂了 → 健康检查踢掉 → **设备端快速重连逻辑兜底**（这是必须做的，别指望 LB 保连接）

### 9.2 单元化 / 分片（千万级以上的正解）

当总连接数到 1 亿级，"全局一张表"就开始出问题，这时候按 **设备 ID / 租户 hash 分片**：

```
DNS ──→ 单元A VIP (设备 0~X)
     ──→ 单元B VIP (设备 X~2X)
     ──→ 单元C VIP ...
```

每个"单元"是独立的 接入网关集群 + Redis + MQ，各自扛自己那份连接。

**好处**：
- 故障爆炸半径小
- 扩容只扩某个单元
- 没有全局热点

这就是阿里/腾讯这类物联网平台的真实做法（**单元化/微服务网格化**）。

### 9.3 每一层的量级是"乘法"关系

- **DNS 层**：把 1 亿设备分摊到 10 个机房 → 每机房 1000 万
- **L4 层**：每机房 1000 万分摊到 10 台 LB → 每台 100 万
- **网关层**：每台 LB 的 100 万再分摊到 10 台网关 → 每台 10 万~50 万（更轻松）

## 十、连接状态管理：不能有单点

- **设备 → 网关 的映射表**放 Redis（或用一致性哈希天然定位）
- 设备在线状态放 Redis，TTL + 心跳续期
- 消息推送时：`业务后端 → Redis 查这台设备挂在哪个网关 → 只给那台网关下发`，而不是广播全网关

---

## 十一、容量估算：先算账再设计

假设 1000 万连接、平均每台设备每 10 秒上报一条 100 字节消息：

- QPS = 1000万 / 10s = **100 万条/秒**
- 带宽 = 100万 × 100B × 8 ≈ **800 Mbps 入口**——单靠几台万兆网卡扛得住，但再加密、再上推流就得上量
- 每台网关 100 万连接 → 每秒 10 万条消息 → 单台网卡 10G 够，CPU 吃紧（epoll 一核可转 50万~100万事件/秒，别跨核锁共享状态）

## 十二、可靠性 / 安全性

| 手段 | 说明 |
|------|------|
| **DDoS 清洗** | IDC 入口前置流量清洗设备，别让 LB 裸奔 |
| **连接级限流** | 单 IP 连接数限制、每秒 accept 限速，防连接耗尽攻击 |
| **心跳与僵尸清理** | 服务端 `tcp_keepalive` + 应用层心跳，定期回收死连接（否则连接数会悄悄涨爆内存） |
| **优雅扩缩容** | 网关下掉前先摘流量（标记 draining），让设备平滑迁移 |
| **降级** | 消息积压时先保连接、丢/缓业务，别让网关被业务拖垮 |

---

## 十三、一句话总结

> **统一入口 = DNS/Anycast 一层 + L4 LB 一层 + 无状态接入网关集群（每台用 epoll + SO_REUSEPORT 扛百万连接）+ 单元化分片到千万亿级；连接与业务解耦、状态进 Redis、消息走 MQ。**

### 每一层的连接归属（终极速查）

```
域名 → 只是解析, 不建连接
 L4 LB(DR) → 不建连接, 只做 MAC 层转发
 网关 RS → 【真正持有长连接的地方】, 用 epoll 管几百万条
  业务后端 → 不持有连接, 通过 MQ 异步消费消息
```

### 三个必背结论

1. **统一入口是逻辑概念**：客户端只看到一个 VIP，背后是 LB 集群 + 每台网关的 lo:0 都绑着同一个 VIP，协同冒充。
2. **L4 LB 扛得住连接，是因为它"不干活"**：不解析不缓存，只在建连时登记一条几百字节的会话，连接空闲期零 CPU 消耗，而且它自己也是一组可水平扩展的机器（DR 模式回包还不经过它）。
3. **真正扛连接的是网关层**：每层各司其职，量级相乘，才有千万级的总容量。
