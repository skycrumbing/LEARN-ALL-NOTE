## 一、Redis 数据存储方式

### 1.1 内存中的 Redis 对象 (robj)

每个 Redis 对象由 `redisObject` 结构描述：

```c
struct redisObject {
    unsigned type:4;      // 对象类型：STRING/LIST/SET/HASH/ZSET
    unsigned encoding:4;  // 底层编码方式
    unsigned lru:24;      // LRU 淘汰时间
    int refcount;         // 引用计数
    void *ptr;            // 指向底层数据结构的指针
};
```

**核心思想：** Redis 用统一的 `robj` 外壳，根据数据规模**自动切换**底层编码，兼顾内存效率和操作性能。

### 1.2 五种核心数据结构及底层编码

| 数据结构 | 小规模编码 | 大规模编码 | 切换阈值 |
|---------|-----------|-----------|---------|
| **STRING** | embstr (≤44字节) | raw (SDS 动态字符串) | >44字节 |
| **LIST** | ziplist (压缩列表) | linkedlist (双端链表) | 元素 >512 且单元素 >64字节 |
| **SET** | intset (整数集合) | hashtable (哈希表) | 含非整数或元素过多 |
| **HASH** | ziplist | hashtable | 同 LIST |
| **ZSET** | ziplist | skiplist + dict (跳跃表+哈希) | 同 LIST |

### 1.3 关键底层结构

**SDS (Simple Dynamic String)**
- 预分配空间避免频繁扩容，记录长度避免遍历，杜绝缓冲区溢出
- `buf[]` 末尾始终有 `\0`，兼容 C 标准库函数

**SkipList (跳跃表) — ZSET 核心**
```
Layer 3:    1 ────────────────────────────── 100
Layer 2:    1 ──────── 50 ───────────────── 100
Layer 1:    1 ── 2 ── 5 ── 50 ── 80 ── 100
```
- 平均查找复杂度 O(logN)
- 相比红黑树：实现简单、插入/删除更高效、更易实现范围查询

### 1.4 持久化机制

```
┌─────────────────────────────────────────────────────────┐
│  RDB (快照式)                                            │
│  • BGSAVE: fork 子进程写快照，主进程继续服务               │
│  • 优点：文件紧凑、恢复快、适合备份                         │
│  • 缺点：可能丢失最后一次 save 之后的数据                   │
├─────────────────────────────────────────────────────────┤
│  AOF (追加式日志)                                        │
│  • 每次写操作追加命令日志                                  │
│  • always:  每命令刷盘 (最安全，最慢)                       │
│  • everysec: 每秒刷盘 (推荐，最多丢1s数据)                 │
│  • no:      交给操作系统 (最快，可能丢很多)                 │
│  • 优点：数据丢失少                                        │
│  • 缺点：文件大、恢复慢、需 AOF rewrite                    │
└─────────────────────────────────────────────────────────┘
```

## 二、为何 Redis 可以做分布式锁

### 2.1 分布式锁的基本要求

1. **互斥性**：同一时刻只有一个客户端持有锁
2. **不会死锁**：持有锁的客户端崩溃后，锁最终能被释放
3. **容错性**：Redis 部分节点故障时，锁仍然可用
4. **可重入性**（可选）：同一客户端可多次获取同一把锁

### 2.2 SETNX 原子性保障

```
┌──────────┐      SETNX key value      ┌──────────┐
│ Client A │  ──────────────────────────►│  Redis   │
│          │  ◄──────────────────────────│  Server  │
└──────────┘  NX=1 → 成功获取锁        └──────────┘

┌──────────┐      SETNX key value      ┌──────────┐
│ Client B │  ──────────────────────────►│  Redis   │
│          │  ◄──────────────────────────│  Server  │
└──────────┘  NX=0 → 获取失败，锁已被占  └──────────┘
```

**SETNX** (SET If Not eXists) 是**原子操作**，Redis 单线程模型保证了即使多个客户端同时竞争，也只有一个能成功。

### 2.3 单实例的致命陷阱

```
时间线:
┌──────┬──────────────┬────────────┬──────────┐
│获取锁│  执行业务     │  (超时)     │  释放锁   │
└──────┴──────┬───────┴─────┬──────┴──────────┘
              │             │
              ▼             ▼
        业务还没执行完    锁已自动过期
                         → 其他客户端获得锁
                         → 并发问题出现！
```

### 2.4 Redisson 看门狗 (Watchdog) 机制

- 默认锁有效期 30s (`lockWatchdogTimeout`)
- 每 10s 检查一次，持有锁的线程仍在执行业务则自动续期
- 只有线程真正执行业务完毕才释放锁

### 2.5 Redlock 算法 (集群锁)

```
Client ───────────────► Redis Node 1  (SETNX + expire)
        │               Redis Node 2  (SETNX + expire)
        │               Redis Node 3  (SETNX + expire)
        │               Redis Node 4
        │               Redis Node 5
        │
        ▼
   如果 多数节点(N/2+1) 成功 且 总耗时 < 锁有效期 → 获取锁成功
```

- 至少需要 5 个独立的 Redis 节点
- 考虑时钟漂移和节点故障

### 2.6 为什么 Redis 适合做分布式锁

| 特性 | 如何满足 |
|------|---------|
| 原子性 | SETNX 单命令原子执行 |
| 高并发 | 单机 10万+ QPS |
| 简单可用 | 部署运维成本低 |
| 过期自动释放 | EXPIRE 防止死锁 |

## 三、Redis IO 模型

### 3.1 Reactor 单线程模型

Redis 采用 **事件驱动 + IO 多路复用 (非阻塞 IO)** 的 Reactor 模式：

```
                ┌─────────────────────────────────────┐
                │         Redis Server (主线程)          │
                │                                     │
  网络请求 ─────►│  IO 多路复用 (epoll/kqueue)          │
                │       │                            │
                │       ▼                            │
                │  事件分派器                          │
                │       │                            │
                │       ├─────────────┬──────────────┤
                │       ▼             ▼              ▼
                │   读事件        写事件        时间事件
                │   (读命令)     (返回结果)     (过期key等)
                │       │             │              │
                │       ▼             ▼              ▼
                │  命令处理器 ──► 写回响应 ──► 定时器
                │                                     │
                └─────────────────────────────────────┘
```

### 3.2 IO 多路复用器选择

| 系统 | 复用器 | 说明 |
|------|--------|------|
| Linux 2.6+ | **epoll** | 高性能 |
| macOS / BSD | **kqueue** | BSD 体系 |
| Solaris | **/dev/poll** | — |
| 其他 | **select** | 兼容 fallback |

### 3.3 为什么单线程 + IO 多路复用能高性能？

| 多线程方案 | IO 多路复用方案 |
|-----------|---------------|
| 每个连接一个线程，等待 IO 时线程被阻塞 | 单线程通过 epoll 监听所有连接 |
| 上下文切换开销、锁竞争、内存占用大 | 就绪事件批量分发，快速处理 |
| 线程数与连接数成正比 | 无锁、无上下文切换、单线程编程简单 |

**关键原因：**
1. **零上下文切换** — 不需要 CPU 在多个线程间调度
2. **无锁** — 不需要互斥锁保护共享数据
3. **命令极快** — 大部分命令 O(1) 或 O(logN)，操作的是内存
4. **IO 多路复用效率高** — 一次系统调用处理多个连接的就绪事件

### 3.4 Redis 6.0+ 多线程 IO

从 6.0 开始引入多线程**网络 IO**（仅读写，执行仍单线程）：

```
                ┌─────────────────────────────────────────┐
                │  多线程 IO (读/写)                        │
                │                                         │
  网络请求 ─────►│  IO 多路复用 (主线程)                     │
                │       │                                 │
                │       ▼                                 │
                │  读事件分派到 多个 IO 线程                │
                │  ┌──────┬──────┬──────┬──────┐          │
                │  │读线程│读线程│读线程│读线程│          │
                │  │  1  │  2  │  3  │  4  │          │
                │  └──┬───┴──┬───┴──┬───┴──┬───┘          │
                │     ▼      ▼      ▼      ▼               │
                │  命令请求队列 (缓冲区)                      │
                │       │                                 │
                │       ▼                                 │
                │  命令执行 (主线程单线程) ──► 返回结果      │
                │       │                                 │
                │       ▼                                 │
                │  写事件分发到 多个 IO 线程                │
                │                                         │
                └─────────────────────────────────────────┘
```

- **多线程只处理网络数据的读/写**（解析命令、序列化响应）
- **命令执行仍在主线程单线程完成**，保证数据一致性
- 默认 IO 线程数 = 4

## 四、最佳使用实践

### 4.1 数据结构选择策略

| 场景 | 推荐结构 | 示例 |
|------|---------|------|
| 计数器 / 唯一 ID | STRING + INCR | 文章阅读量、订单号 |
| 缓存 / 简单存储 | STRING | 用户信息 JSON |
| 消息队列 | LIST / Stream | 任务队列、消息系统 |
| 标签 / 去重 | SET | 用户标签、共同好友 |
| 对象字段缓存 | HASH | 用户资料 (name/age/city) |
| 排行榜 / TopN | ZSET | 游戏积分、热搜榜 |
| 位统计 | BITMAP | 签到、活跃用户 |
| 基数统计 | HyperLogLog | 独立访客数 (UV) |
| 地理位置 | GEO | 附近门店查询 |

### 4.2 Key 设计规范

```
✅ 好:  user:10001:profile    (冒号分隔，层级清晰)
✅ 好:  order:20240115:8888   (业务前缀 + 时间 + ID)
❌ 坏:  a                        (无意义)
❌ 坏:  单个 key 值过大 (>10KB)  (影响性能)
```

**原则：**
- 加业务前缀区分命名空间
- 保持简洁但可读
- 避免无过期时间的 key（防止内存泄漏）
- 单个 key 的 value 尽量控制在 10KB 以内

### 4.3 性能优化

```
1. 批量操作
   ✗ N 次单独请求: SET k1 v1, SET k2 v2 ...  (网络开销 ×N)
   ✓ Pipeline:   一次性发送 N 条命令            (网络开销 ×1)
   ✓ MGET / MSET:  单命令批量读写

2. 避免在大集合上执行 O(N) 命令
   ✗ KEYS *       → O(N) 全库扫描
   ✓ SCAN cursor  → 渐进式扫描
   ✗ HGETALL      → O(N)
   ✓ HSCAN cursor → 渐进式扫描

3. 合理设置过期时间
   • 热点数据: TTL 短 (秒级~分钟级)
   • 缓存数据: TTL 长 + 主动更新
   • 重要数据: 持久化到数据库，Redis 做缓存

4. 使用集群避免单点
   • 单机: < 5GB 数据
   • Redis Cluster: 16384 个 hash slot 分片
```

### 4.4 缓存与数据库一致性

**Cache Aside（旁路缓存）★ 推荐**

```
读:  查缓存 → 命中返回 / 未命中查 DB → 写缓存 → 返回
写:  更新 DB → 删除缓存 (不是更新缓存!)
理由: 删除 + 延迟加载 比 更新缓存 更不容易出现脏数据
```

### 4.5 缓存问题应对

```
┌─────────────────────────────────────────────────────────┐
│  缓存穿透 (查询不存在的数据)                               │
│  • 布隆过滤器 (Bloom Filter) 预先拦截                     │
│  • 缓存空值 (给不存在的结果设短 TTL)                       │
├─────────────────────────────────────────────────────────┤
│  缓存击穿 (热点 key 突然过期)                              │
│  • 互斥锁 (SETNX) 保证只有一个请求回源                     │
│  • 永不过期的热点 key (逻辑过期)                           │
├─────────────────────────────────────────────────────────┤
│  缓存雪崩 (大量 key 同时过期)                              │
│  • TTL 加随机值 (避免同时过期)                             │
│  • 多级缓存 (L1 本地 + L2 Redis)                         │
│  • 限流降级                                              │
├─────────────────────────────────────────────────────────┤
│  热点数据倾斜 (单 key 访问量极高)                           │
│  • 本地缓存 (Caffeine/Guava)                             │
│  • Redis 集群虚拟热点 (拆分 key)                          │
└─────────────────────────────────────────────────────────┘
```

## 五、可能存在的问题与风险

### 5.1 内存溢出 (OOM)

```
maxmemory 设置不足 + 无淘汰策略 → OOM

解决:
  • 合理设置 maxmemory (建议不超过物理内存 70%)
  • 选择淘汰策略:
    ┌─────────────────────────────────────────────────┐
    │ allkeys-lru       所有 key 的 LRU  ★ 最常用       │
    │ allkeys-random    随机淘汰                       │
    │ volatile-lru      仅带 TTL 的 key 的 LRU          │
    │ volatile-ttl      按 TTL 排序，先过期先删         │
    │ noeviction        不淘汰，写操作报错 ★ 安全保守   │
    └─────────────────────────────────────────────────┘
```

### 5.2 大 Key (Big Key)

```
危害:
  • 网络 IO 阻塞: 一个 big key 几百 KB~几 MB，单次传输耗时大
  • 单线程阻塞: DEL 操作 O(N)，阻塞 Redis 主线程
  • 集群数据倾斜: 一个 slot 数据量过大

检测:
  • redis-cli --bigkeys    (快速扫描)
  • redis-cli --hotkeys    (查找热点 key)
  • MEMORY USAGE <key>     (查看单个 key 内存)

解决:
  • 拆分大 key (hash 分片、list 分段)
  • 用 UNLINK 替代 DEL (异步删除)
  • 用 HSCAN 替代 HGETALL (渐进式处理)
```

### 5.3 热 Key (Hot Key)

```
场景: 秒杀商品，单 key 访问量 10万+ QPS

影响:
  • 单个 Redis 节点被打爆，其他节点空闲
  • 集群负载极度不均

解决:
  • 客户端本地缓存 + Redis 缓存 (多级)
  • 数据拷贝/分片: 将热点 key 复制到多个节点
  • 读写分离: 主从架构，读走从库
```

### 5.4 主从切换与数据丢失

```
主从复制流程:
  ┌──────┐    全量同步      ┌──────┐
  │Master│ ────────────────►│Slave │
  └──┬───┘                  └──┬───┘
     │  增量同步 (持续)          │
     │◄─────────────────────── │

风险:
  • 异步复制: Master 宕机前，部分命令未同步到 Slave
  • 脑裂 (Split Brain): 网络分区时，两个 Master 同时存在
  • 自动故障转移可能选到数据不全的 Slave

解决:
  • Redis Sentinel: 监控 + 自动故障转移
  • Redis Cluster: 多数派写入，避免脑裂
  • min-replicas-to-write: 至少 N 个 slave 确认才返回
```

### 5.5 集群模式问题

```
┌─────────────────────────────────────────────────────────┐
│  1. 哈希槽 (16384 slots) 倾斜                            │
│     → 使用虚拟 slot 均衡 (tag hint)                      │
│                                                         │
│  2. MOVED/ASK 重定向开销                                 │
│     → 客户端维护槽位映射表                               │
│                                                         │
│  3. 跨 slot 操作不支持                                     │
│     → MGET k1 k2 (在不同 slot) 会报错                    │
│     → 使用 hash tag: {user1000}:friend1                  │
│                                                         │
│  4. Pipeline 无法跨节点                                    │
│     → 同一 pipeline 中的 key 必须在同一 slot              │
│                                                         │
│  5. Redis Cluster 不支持多数据库 (SELECT 0-15)          │
│     → 只能用 SELECT 0                                   │
└─────────────────────────────────────────────────────────┘
```

### 5.6 Lua 脚本阻塞

```
• Lua 脚本原子执行，长时间运行会阻塞主线程
• 解决: 脚本控制在毫秒级，超时后 SCRIPT KILL 终止
• 避免在脚本中使用 KEYS * 等不可控操作
```

### 5.7 安全与运维

| 问题 | 措施 |
|------|------|
| 未授权访问 | requirepass + rename-command |
| 内存泄漏 | 监控 used_memory + 定期 bigkey 扫描 |
| 慢查询 | slowlog-log-slower-than 监控 |
| 连接数过多 | 配置 maxclients + 连接池 |
| 数据误删 | 开启 AOF + 定期 RDB + 备份策略 |

## 六、Redis 做消息队列

Redis 可以做消息队列，有三种方案，能力逐级递增。

> **核心前提：** 三种方案都依赖消费者与 Redis 的 **TCP 长连接**——Redis 的 Reactor 单线程模型中，阻塞等待（BRPOP/XREAD BLOCK）和事件推送（Pub/Sub）都需要这条连接持续存在。断连意味着无法接收新消息。

---

### 6.1 LIST（RPUSH + LPOP / BRPOP）

#### 底层数据结构

LIST 底层是 **quicklist（Redis 5.0+）**，由多个 ziplist 组成的双端链表：

```
quicklist 结构:

  ┌───────────┐     ┌───────────┐     ┌───────────┐
  │ ziplist1  │────►│ ziplist2  │────►│ ziplist3  │  ──► null
  └───────────┘     └───────────┘     └───────────┘
  ▲                                                       ┘
  └─────────────────────────────────────────────────────────┘
  head                                                          tail

  每个 ziplist 内部:
  ┌──────┬──────┬──────┬──────┐
  │ job1 │ job2 │ job3 │ job4 │
  └──────┴──────┴──────┴──────┘
```

#### RPUSH 为什么 O(1)？

```
步骤:
  1. 直接取 tail 指针 → O(1)，无需遍历
  2. 在尾部的 ziplist 中追加元素
  3. 如果 ziplist 达到容量上限，创建新 ziplist 节点并链接

不需要遍历整个列表，一步到位。
```

#### LPOP 为什么 O(1)？

```
步骤:
  1. 直接取 head 指针 → O(1)
  2. 从头部 ziplist 弹出首元素
  3. 如果 ziplist 变空，释放该节点，更新 head 指针
```

#### BRPOP 阻塞原理 — 事件通知，非轮询

```
客户端A:  BRPOP queue:task 30
          → 主线程发现队列为空
          → 将客户端A加入 queue:task 的 blocked client 列表
          → 客户端A状态变为 BLOCKED，主线程继续处理其他命令

客户端B:  RPUSH queue:task job5
          → 数据插入成功
          → 主线程扫描 blocked client 列表
          → 发现客户端A在等 queue:task
          → 将 job5 返回给客户端A，解除阻塞

关键: 不是轮询，而是事件通知。
      Redis 内部有一个 blocked 列表，
      当写操作触发 key 变化时，通知等待者。
```

#### 局限

- 消息弹出即消失，消费者崩溃则消息永久丢失
- 无 ack 机制，无法保证至少消费一次
- 不支持消息回溯和重放
- **断连后：已弹出的消息无法恢复**

### 6.2 Pub/Sub（PUBLISH + SUBSCRIBE）

#### 核心数据结构

Redis 内部维护两个映射表：

```
┌─────────────────────────────────────────────────────┐
│  1. pubsub_channels: channel → 订阅者集合            │
│                                                      │
│  "channel:news" ──► { client1, client2 }            │
│  "channel:chat" ──► { client3, client4 }            │
│                                                      │
├─────────────────────────────────────────────────────┤
│  2. pubsub_patterns:  glob模式 → 订阅者集合           │
│                                                      │
│  "channel:*"    ──► { client5 }                     │
│  "user:*:msg"   ──► { client6 }                     │
└─────────────────────────────────────────────────────┘
```

#### SUBSCRIBE 发生了什么

```
客户端A:  SUBSCRIBE channel:news
         → 将 clientA 加入 pubsub_channels["channel:news"]
         → 设置 clientA 状态为 SUBSCRIBING
         → 返回确认消息

客户端从此进入"订阅模式"，
只接收消息，不再处理普通命令。
```

#### PUBLISH 发生了什么

```
客户端B:  PUBLISH channel:news "hello"
         → 查找 pubsub_channels["channel:news"] → { client1, client2 }
         → 遍历订阅者，将消息写入每个 client 的 pending 响应队列
         → 查找 pubsub_patterns 中匹配 "channel:news" 的模式
         → 同样写入匹配订阅者的响应队列
         → 返回订阅者总数

         消息分发完成后即丢弃，不持久化。
```

#### 为什么不持久化？

```
设计本质: Pub/Sub 是纯内存事件分发，不是消息存储

消息生命周期:
  PUBLISH 发出 → 立即分发到所有已订阅客户端 → 丢弃

无订阅者时:
  PUBLISH channel:news "hello"
  → 查找订阅者 → 0 个
  → 直接丢弃
  → 返回 (integer) 0

即 "fire and forget"（即发即忘）
```

#### 集群中的问题

```
Redis Cluster 中:
  每个节点独立维护自己的 pubsub_channels
  PUBLISH 只投递到当前节点上的订阅者
  → 跨节点的消息收不到

官方建议: 集群模式下不要用 Pub/Sub
```

#### 局限

- **断连后：离线期间消息全部丢失，无法恢复**
- 无 ack、无重试、无优先级

### 6.3 Stream（5.0+，★ 推荐）

#### 底层数据结构 — radix tree + skip list

```
Radix Tree（基数树/字典树）:

  根节点
   ├── 1- 分支 (ID 以 "1-" 开头)
   │    ├── 7- 分支
   │    │    ├── 0000000000-0  →  {msg1字段}
   │    │    ├── 0000000001-0  →  {msg2字段}
   │    │    ├── 0000000002-0  →  {msg3字段}
   │    │    └── ...
   │    └── ...
   └── ...

特点:
  • 前缀共享: 共同前缀只存一次，节省内存
  • 快速定位: 根据消息ID O(logN) 找到对应节点
  • 自动扩容: 每条消息是树中的一个叶子节点
```

#### 消息 ID 的设计

```
格式: timestamp-sequence

例子:
  1700000000000-0
  1700000000000-1    ← 同一毫秒，序列号递增
  1700000000001-0

• 前半部分: 毫秒时间戳，保证大致递增
• 后半部分: 同一毫秒内的序列号

为什么用时间戳？
  → 时间戳本身有意义（可按时间范围查询）
  → 天然有序，无需额外排序
  → 即使消息被删除，ID 不重复
```

#### XADD 写入流程

```
XADD stream:orders * user_id 1001 amount 999.00

主线程:
  1. ID 为 * → 基于当前时间生成下一个 ID
  2. 在 radix tree 中创建叶子节点
  3. 存储消息字段 (key-value pairs)
  4. 更新 stream 元数据:
     • 最后一条消息 ID
     • 消息总数
     • 如果有 maxlen 限制，执行 TRIM 删除最旧消息
  5. 返回消息 ID
```

#### 消费者组 — Stream 最核心的机制

每个 Stream + 消费者组维护 **三个关键状态**：

```
┌─────────────────────────────────────────────────────────────────┐
│  Stream: stream:orders                                           │
│                                                                   │
│  状态1: last-id-delivered (消费者组级别)                           │
│     → 记录该消费者组"最后一条已投递的消息ID"                       │
│     → 每个消费者组独立维护，互不干扰                               │
│                                                                   │
│  状态2: 每个 consumer 的 pending list (待确认列表)                 │
│     → 记录: 我领了哪些消息还没确认                                 │
│     → 格式: { messageID → { consumer名, 交付时间, 未ACK次数 } }  │
│                                                                   │
│  状态3: radix tree 中的消息本身                                    │
│     → 消息永远不会因为"被消费"而删除                              │
│     → 只有达到 maxlen 限制时才会被 TRIM 掉                        │
└─────────────────────────────────────────────────────────────────┘
```

#### XREADGROUP 完整流程

```
消费者组 group1 中有两个消费者: consumer1、consumer2

步骤 1: XGROUP CREATE stream:orders group1 $
  → 为 stream:orders 创建 group1 元数据
  → last-id-delivered = $ (当前最新 ID，从此开始接收)

步骤 2: consumer1 执行
        XREADGROUP GROUP group1 consumer1 STREAMS stream:orders >
  → Redis 检查 group1.last-id-delivered
  → 发现新消息 ID=5
  → 将 ID=5 返回给 consumer1
  → 同时:
    a. 更新 last-id-delivered = 5
    b. 将 {5 → {consumer1, time, count=1}} 加入 consumer1 的 pending list
  → consumer1 开始处理...

步骤 3: consumer2 执行
        XREADGROUP GROUP group1 consumer2 STREAMS stream:orders >
  → 检查 last-id-delivered = 5
  → 发现新消息 ID=6
  → 返回 ID=6 给 consumer2
  → 更新 last-id-delivered = 6
  → 加入 consumer2 的 pending list

关键: 每个消息只分配给一个消费者（至少消费一次）
     但消息不从 stream 中移除！

步骤 4: consumer1 处理完毕
        XACK stream:orders group1 5
  → 从 consumer1 的 pending list 移除 ID=5
  → 消息标记为"已确认"

如果 consumer1 崩溃，未发送 XACK:
  → ID=5 仍在 consumer1 的 pending list 中
  → XPENDING 可查看: "consumer1 有 1 条未确认消息，已 30 秒"
  → 应用可重取这条消息进行重试
```

#### BLOCK 阻塞原理

```
与 BRPOP 相同的事件通知机制:

1. 主线程检查 stream 是否有新消息
2. 没有 → 客户端状态变为 BLOCKED
3. 客户端加入该 stream 的 wait 列表
4. 主线程继续处理其他命令
5. 有新消息到达 → 唤醒等待中的客户端
6. 超时 → 解除阻塞，返回空结果
```

#### 消息清理机制

```
消息不会被"消费"删除，如何防止无限增长？

方式 1: maxlen (写入时自动截断)
  XADD stream:orders * maxlen 1000 field1 value1

方式 2: XTRIM (手动截断)
  XTRIM stream:orders MAXLEN 1000
  → 删除最旧的消息，保留最新 1000 条

方式 3: MINID (按 ID 截断)
  XTRIM stream:orders MINID 1700000000000-0
  → 删除 ID 小于指定值的所有消息
```

#### 断连后恢复

```
这是 Stream 最大的优势:

Consumer 断连 → 消息仍在 radix tree 中
               → 未确认的消息在 pending list 中
               → 重连后通过 XPENDING 查看未确认消息
               → 重取后继续消费

实现"至少消费一次"（at-least-once）语义。
```

```
┌──────────────────────────────────────────────────────────────────────┐
│                        底层数据结构                                    │
├──────────┬───────────────────────────────────────────────────────────┤
│  LIST    │  quicklist (ziplist + 双端链表)                            │
│          │  • 写入: 尾指针 + 新增节点 = O(1)                          │
│          │  • 读取: 头指针 - 节点 = O(1)                              │
│          │  • 阻塞: blocked client 列表 + 事件通知                    │
│          │  • 断连: 弹出消息永久丢失                                   │
├──────────┼───────────────────────────────────────────────────────────┤
│  Pub/Sub │  channel → subscriber 映射表                               │
│          │  • 订阅: 往映射表插入客户端引用                             │
│          │  • 发布: 查找订阅者 → 遍历推送 → 丢弃                      │
│          │  • 无状态: 没有持久化结构                                   │
│          │  • 断连: 离线消息全部丢失                                   │
├──────────┼───────────────────────────────────────────────────────────┤
│  Stream  │  radix tree + skip list + 消费者组元数据                   │
│          │  • 存储: 前缀共享基数树，内存效率高                         │
│          │  • 投递: last-id-delivered 追踪消费者组进度                 │
│          │  • 确认: pending list 追踪未确认消息                        │
│          │  • XACK 从 pending list 移除                               │
│          │  • 断连: 消息仍在，重连后可通过 XPENDING 恢复               │
└──────────┴───────────────────────────────────────────────────────────┘
```

## 七、Redis 客户端：Jedis vs Lettuce

> 学了 Redis 原理，下一步是 **怎么连接 Redis**。Java 生态中最主流的两个客户端：Jedis 和 Lettuce。

### 7.1 基本对比

| 维度 | Jedis | Lettuce |
|------|-------|---------|

### 7.2 Jedis 架构 — BIO 阻塞模型

```
┌─────────────────────────────────────────────────────────────────┐
│  Jedis 的核心问题: 一连接只能被一个线程使用                         │
│                                                                  │
│  传统用法 (每个线程独立连接):                                      │
│                                                                  │
│  Thread-1 ──► Jedis (连接1) ──► Redis                            │
│  Thread-2 ──► Jedis (连接2) ──► Redis                            │
│  Thread-3 ──► Jedis (连接3) ──► Redis                            │
│  Thread-N ──► Jedis (连接N) ──► Redis                            │
│                                                                  │
│  N 个线程 = N 条 TCP 连接                                         │
│  1000 个线程 = 1000 条 TCP 连接                                    │
│                                                                  │
│  问题:                                                           │
│  • 一个 TCP 连接占用 ~64KB 内核内存                               │
│  • 1000 连接 = 64MB 内核内存（仅连接层面）                          │
│  • Redis 服务端 maxclients 默认 10000，很快被打满                  │
│  • 线程切换开销大                                                  │
└─────────────────────────────────────────────────────────────────┘

Jedis 解决方式: 连接池

┌─────────────────────────────────────────────────────────────────┐
│  JedisPool (连接池):                                             │
│                                                                  │
│  ┌─────────────────────────────────────┐                        │
│  │  空闲连接列表                         │                        │
│  │  [conn1, conn2, conn3, conn4, ...]  │                        │
│  └──────────────────┬──────────────────┘                        │
│                     │                                             │
│  Thread-1 ──── 借出 conn1 ──► 使用 ──► 归还 ──► 池              │
│  Thread-2 ──── 借出 conn2 ──► 使用 ──► 归还 ──► 池              │
│  Thread-3 ──── 借出 conn3 ──► 使用 ──► 归还 ──► 池              │
│                                                                  │
│  如果池中无空闲连接:                                               │
│  → 等待 maxWaitMillis（超时则抛异常）                               │
│  → 或如果 active 未达 maxActive，则新建连接                        │
└─────────────────────────────────────────────────────────────────┘
```

### 7.3 Lettuce 架构 — NIO 非阻塞模型

```
┌─────────────────────────────────────────────────────────────────┐
│  Lettuce 的核心优势: 单连接可被多个线程共享                          │
│                                                                  │
│  ┌──────────────────────────────────────────────┐               │
│  │  Lettuce 内部结构:                             │               │
│  │                                               │               │
│  │  ┌─────────────┐    ┌──────────────┐         │               │
│  │  │ CommandQueue │───►│ Channel      │         │               │
│  │  │ (线程安全队列)│    │ (Netty NIO)  │         │               │
│  │  └─────────────┘    └──────┬───────┘         │               │
│  │                            │                   │               │
│  │  Thread-1 ── 放入命令 ────┘                   │               │
│  │  Thread-2 ── 放入命令 ──┐                     │               │
│  │  Thread-3 ── 放入命令 ──┤                     │               │
│  │  Thread-N ── 放入命令 ──┘                     │               │
│  │                                               │               │
│  │  Netty 事件循环读取 Redis 响应 → 按序匹配回  │               │
│  │  放入各线程的 Future/Promise 中              │               │
│  └──────────────────────────────────────────────┘               │
│                                                                  │
│  核心机制:                                                        │
│  • 所有线程通过线程安全的队列（ConcurrentLinkedQueue）            │
│    向同一条 Channel 放入命令                                       │
│  • Netty 的 NIO 事件循环从 Channel 读取响应                      │
│  • 根据命令与响应的对应关系，将结果写回各自的 Future               │
│  • 结果: 1 条连接处理 100 个线程的并发请求                         │
└─────────────────────────────────────────────────────────────────┘
```

### 7.3.1 为什么 Jedis 不能用单连接 + 线程安全队列？

> 理论上不是完全不能，而是以 Jedis 当前的 BIO 架构，无法实现。问题在于"发出去容易，收回来匹配难"。

**核心问题：BIO 模式下，响应如何匹配到正确的线程？**

```
假设强行给 Jedis 加一个 ConcurrentLinkedQueue：

  Thread-1 ──┐
  Thread-2 ──┼──► CommandQueue ──► 单连接 ──► Redis
  Thread-3 ──┘

                 │
                 ▼
         Redis 返回响应 → ???
```

Redis 的命令和响应是 **1:1 对应** 的：

```
正常（Lettuce 的方式）：
  线程A 发 SET k1 v1    → 等待 FutureA
  线程B 发 GET k1        → 等待 FutureB
  线程C 发 INCR counter  → 等待 FutureC

  Redis 返回: "+OK"        → 唤醒 FutureA ✓
  Redis 返回: "$3\r\nv1"   → 唤醒 FutureB ✓
  Redis 返回: ":42"         → 唤醒 FutureC ✓

  → 每个命令发出时绑定了一个 Future
  → 收到的响应按顺序依次 resolve 对应的 Future
```

但这里有一个前提条件：

```
┌─────────────────────────────────────────────────────────────┐
│  发送端: 所有命令串行化发出（没问题，队列保证）                  │
│  接收端: 必须能识别"这是第几个响应" → 对应第几个命令           │
│                                                              │
│  在 NIO 中 (Lettuce):                                        │
│    → Netty 的 Channel 每次收到数据触发一个事件                  │
│    → 事件处理器知道当前读了哪个命令的响应                       │
│    → 用同一个 Future 序列依次 resolve                          │
│                                                              │
│  在 BIO 中 (Jedis):                                          │
│    → socket 的 InputStream.read() 是阻塞的                    │
│    → 哪个线程调了 read()，哪个线程就被卡在那里                 │
│    → 这个线程读完响应后，怎么知道该唤醒哪个调用者？             │
│    → 必须有一个专门的线程持续在 read()，才能解耦               │
└─────────────────────────────────────────────────────────────┘
```

**那 Jedis 真的完全做不到吗？**

```
┌─────────────────────────────────────────────────────────────────┐
│  如果要在 Jedis 上实现"单连接 + 多线程共享"，需要改三件事:       │
│                                                                  │
│  1. 拆出"发送线程"和"接收线程"                                    │
│     → 主线程把命令放到队列                                         │
│     → 专门的接收线程阻塞在 read() 上                             │
│                                                                  │
│  2. 引入 Future/Promise 机制                                       │
│     → 每个命令发出时生成一个 Future                              │
│     → 接收线程读到响应后 resolve 对应的 Future                   │
│     → 调用者阻塞在 Future.get() 上                              │
│                                                                  │
│  3. 处理 TCP 粘包/拆包                                             │
│     → Redis 用 RESP 协议，消息边界明确                           │
│     → 但连续多个响应可能在一次 read() 中全部到达                   │
│     → 需要按 RESP 规则逐条解析                                    │
│                                                                  │
│  ─────────────────────────────────────────────                    │
│                                                                  │
│  改完之后，Jedis 就变成了 Lettuce                                │
│                                                                  │
│  这就是 Lettuce 的存在意义。                                     │
└─────────────────────────────────────────────────────────────────┘
```

**本质区别：**

```
┌─────────────────────────────────────────────────────────────────┐
│  Jedis 的本质: 同步请求-响应模型                                  │
│                                                                  │
│  Thread ── write() ──► socket ──► Redis                        │
│  Thread ◄── read()  ◄── socket ◄── Redis                      │
│                                                                  │
│  同一个线程既要写又要读，写完了就阻塞在读上                       │
│  这个线程被占用了，其他人没法用这条连接                            │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  Lettuce 的本质: 异步请求-响应模型                                │
│                                                                  │
│  Thread ── 放入命令 + 等待 Future ──► CommandQueue             │
│                                                                  │
│  Netty (专门的事件循环线程) ── write() ──► socket ──► Redis    │
│  Netty ◄── read()  ◄── socket ◄── Redis                       │
│         └── 解析响应 → resolve Future → 唤醒 Thread            │
│                                                                  │
│  调用线程不阻塞 IO，只阻塞 Future.get()                           │
│  Netty 的事件循环独占这条连接的 IO，所有线程共享                  │
└─────────────────────────────────────────────────────────────────┘

本质原因一句话:

  Jedis 的 socket 是阻塞模式的，read() 一调用，当前线程就被占用。
  要让一个线程"发"、另一个线程"收"，必须把 socket 设成非阻塞模式，
  用 NIO + Selector 才能做到——而那正是 Netty/Lettuce 做的事。
  Jedis 不引入 NIO，就做不到单连接多线程共享。
```

### 7.4 连接池原理

```
┌─────────────────────────────────────────────────────────────────┐
│  为什么需要连接池？                                                │
│                                                                  │
│  TCP 连接建立成本:                                                │
│  • 三次握手 (1~3 RTT)                                            │
│  • TLS 握手 (如果启用加密，额外 1~2 RTT)                         │
│  • 每次新建连接都需要这个开销                                    │
│                                                                  │
│  连接池解决的问题:                                                │
│  • 复用已建立的连接，避免反复握手                                  │
│  • 控制最大连接数，防止打爆服务端                                  │
│  • 空闲连接定期检测，剔除死连接                                    │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  关键配置参数:                                                     │
│                                                                  │
│  maxTotal (maxActive):   池中最大连接数                            │
│  maxIdle:                池中最空闲连接数                           │
│  minIdle:                池中最少空闲连接数                         │
│  maxWaitMillis:          获取连接的最大等待时间                     │
│  testOnBorrow:           借出时是否检查连接是否有效 (建议开启)      │
│  testWhileIdle:          空闲时是否检测 (避免用死连接)              │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  生命周期:                                                        │
│                                                                  │
│  创建连接池                                                      │
│    → 初始化 minIdle 个连接（或直接延迟创建）                      │
│                                                                  │
│  线程请求连接:                                                    │
│    → 池中有空闲连接 → 直接返回                                   │
│    → 池中无空闲 + active < maxTotal → 新建                       │
│    → 池中无空闲 + active = maxTotal → 等待 / 抛异常              │
│                                                                  │
│  线程归还连接:                                                    │
│    → 标记为空闲，放回池                                           │
│    → 如果 idle > maxIdle → 关闭多余连接                          │
│                                                                  │
│  定期检测:                                                        │
│    → 检测空闲时间超过 idleTimeout 的连接 → 关闭                  │
│    → 检测已关闭/断连的连接 → 移除                                 │
│                                                                  │
│  关闭连接池:                                                      │
│    → 关闭所有连接，回收资源                                        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 7.5 线程安全模型对比

```
┌─────────────────────────────────────────────────────────────────┐
│  Jedis: 线程不安全                                               │
│                                                                  │
│  原因: Jedis 内部的 IO 状态（读写位置）是非线程安全的             │
│  → 两个线程共享同一个 Jedis 实例会数据错乱                        │
│  → 解决方案: 每个线程用自己的连接，或从连接池借                   │
│                                                                  │
│  代码:                                                            │
│  Jedis jedis = jedisPool.getResource();                          │
│  try {                                                           │
│      jedis.set("key", "value");                                  │
│  } finally {                                                     │
│      jedis.close();  // 实际是归还到连接池                        │
│  }                                                                │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  Lettuce: 线程安全                                               │
│                                                                  │
│  原因: 内部使用线程安全的命令队列 + Netty 事件循环                │
│  → 多个线程共享同一个 RedisClient 实例是安全的                   │
│  → 每个线程的命令通过队列放入，按序执行                          │
│  → 命令与响应通过 Future 机制配对，不会串                           │
│                                                                  │
│  代码:                                                            │
│  StatefulRedisConnection conn = client.connect();                 │
│  RedisCommands commands = conn.sync();                            │
│  commands.set("key", "value");  // 多线程安全共享                  │
│                                                                  │
│  异步方式:                                                        │
│  RedisCommandsAsync async = conn.async();                        │
│  async.set("key", "value").thenAccept(result -> {...});          │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 7.6 为什么 Spring Boot 2.x 默认从 Jedis 换成了 Lettuce？

```
┌─────────────────────────────────────────────────────────────────┐
│  原因 1: 线程效率                                                │
│                                                                  │
│  Jedis 场景: 100 个并发线程 → 100 条 TCP 连接                   │
│  Lettuce 场景: 100 个并发线程 → 1 条 TCP 连接                   │
│                                                                  │
│  在生产环境中，连接数是宝贵资源:                                   │
│  • Redis 服务端 maxclients 默认 10000                           │
│  • 如果系统有 5000 个线程并发访问 Redis                            │
│    → Jedis 需要 5000 连接，占用大量资源                          │
│    → Lettuce 只需要 1 连接，节省 5000 倍                          │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  原因 2: 原生异步支持                                             │
│                                                                  │
│  Lettuce 原生支持异步 (CompletableFuture) + 响应式 (Reactor)     │
│  → 适配 Spring WebFlux (响应式栈)                               │
│  → Jedis 是纯同步阻塞，不支持异步                                │
│  → Spring Boot 2.x 引入了 WebFlux 作为非阻塞 Web 框架             │
│    用 Jedis 需要额外线程池包装，不优雅                            │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  原因 3: Pub/Sub 支持                                            │
│                                                                  │
│  Jedis 的 Pub/Sub 是阻塞的:                                      │
│    订阅后线程被占用，无法做其他事                                 │
│    每多一个 channel 就要多一个线程                                 │
│                                                                  │
│  Lettuce 的 Pub/Sub 是非阻塞的:                                   │
│    基于 Netty 事件循环，订阅不占用线程                             │
│    一个线程可订阅多个 channel                                     │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  原因 4: 集成 Redis Sentinel / Cluster 更优雅                     │
│                                                                  │
│  Lettuce 用统一的 RedisClient API 支持多种拓扑:                   │
│    • 单机: client.connect()                                     │
│    • Sentinel: client.connect(ReadFrom.SLAVE_PREFERRED)          │
│    • Cluster: client.connect() 自动发现                          │
│                                                                  │
│  Jedis 每种拓扑需要不同的类:                                      │
│    • Jedis、JedisPool、JedisSentinelPool、JedisCluster           │
│    代码分散，维护成本高                                            │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  原因 5: Lettuce 的演进                                           │
│                                                                  │
│  • Jedis 发展较慢，长期缺乏异步支持                               │
│  • Lettuce 从 1.0 开始就基于 Netty，技术栈现代                    │
│  • Spring Data Redis 在 2.x 中重构，全面切换 Lettuce              │
│  • 社区活跃度 Lettuce > Jedis                                    │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│  Jedis 的反击: Jedis 3.x + Jedis 4.x                            │
│                                                                  │
│  • Jedis 4.x 基于 Java 17，部分优化了性能                         │
│  • 但本质上仍是 BIO，架构差异无法弥补                             │
│  • 社区推荐新项目用 Lettuce                                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 7.7 实际使用建议

```
┌─────────────────────────────────────────────────────────────────┐
│  新项目: 直接选 Lettuce (Spring Boot 默认就是)                    │
│                                                                  │
│  遗留项目用 Jedis:                                                │
│  ✓ 确保搭配 JedisPool 使用，不要用单例 Jedis                     │
│  ✓ 注意在 finally 块中归还连接                                    │
│  ✓ 连接池参数根据并发量合理配置                                   │
│                                                                  │
│  性能选型:                                                        │
│  • 低并发 (< 50 线程)     → 两者性能差异不明显                     │
│  • 高并发 (500+ 线程)     → Lettuce 优势明显                      │
│  • 需要异步/响应式        → 只能选 Lettuce                         │
│  • 需要 Pub/Sub           → Lettuce 优势明显                       │
│  • Redis 集群/Sentinel    → Lettuce 代码更简洁                    │
│                                                                  │
│  常见误区:                                                        │
│  ✗ 把 Jedis 实例做成单例让多线程共享 (线程不安全)                  │
│  ✗ 用 Jedis 但不归还连接 (连接泄漏)                               │
│  ✗ Lettuce 连接数设太小，导致所有请求排队等待                     │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```
