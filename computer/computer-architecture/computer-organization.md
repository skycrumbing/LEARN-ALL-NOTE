## 一、冯·诺依曼架构——计算机长什么样？

### 1.1 五大部件

```
                           ┌──────────────┐
                           │    主存储器    │  ← 程序和数据都存在这里
                           │  (RAM)       │    (不区分"代码区"和"数据区")
                           └──┬────────┬──┘
                              │  ↑     │  ↓
                        数据总线 地址总线  控制总线
                              │  │     │  │
┌──────────┐            ┌─────┴──┴─────┴──┴─────┐          ┌──────────┐
│  输入设备  │ ────────→ │      控制器 + 运算器     │ ────────→ │  输出设备  │
│ (键盘/网卡)│           │      (CPU)              │          │ (显示器)  │
└──────────┘            └────────────────────────┘          └──────────┘
```

**核心思想**：程序和数据都存在同一个存储器里。这意味着**程序可以被当作数据来修改**——这是操作系统加载程序、编译器生成代码的基础。

### 1.2 现场感受

## 二、CPU 内部——数据怎么流动？

### 2.1 寄存器：CPU 手里捏着的数据

寄存器是 CPU 内部**最快的存储**——存取只需 1 个时钟周期。CPU 做运算时，数据必须先从内存加载到寄存器。

```
x86-64 CPU 的关键寄存器：
┌────────────────────────────────────────────┐
│ RAX   累加器  (函数返回值放这里)              │
│ RBX   基址    (通用)                        │
│ RCX   计数器  (循环次数)                     │
│ RDX   数据    (通用)                        │
│ RSI   源索引  (字符串操作的源地址)            │
│ RDI   目标索引 (字符串操作的目标地址)         │
│ RSP   栈指针  (指向当前函数栈帧的顶部)        │
│ RBP   基指针  (指向当前函数栈帧的底部)        │
│ RIP   指令指针 (下一条要执行的指令地址)        │
└────────────────────────────────────────────┘
```

### 2.2 动手：看一段 C 代码编译后的汇编（寄存器在干活）

```bash
# 写一个最简单的 C 程序
cat > /tmp/cpu-demo.c << 'EOF'
#include <stdio.h>
int add(int a, int b) {
    int sum = a + b;
    return sum;
}
int main() {
    int x = 3, y = 5;
    int result = add(x, y);
    printf("3 + 5 = %d\n", result);
    return 0;
}
EOF

# 编译成汇编（-S = 生成汇编, -O0 = 不优化, 便于看懂）
gcc -S -O0 -o /tmp/cpu-demo.s /tmp/cpu-demo.c

# 看 add 函数的汇编代码
sed -n '/^add:/,/\.cfi_endproc/p' /tmp/cpu-demo.s
```
```
add:
    pushq   %rbp            ; 保存调用者的栈基址
    movq    %rsp, %rbp      ; 建立自己的栈帧
    movl    %edi, -20(%rbp) ; 第1个参数 a (在 edi 中) → 栈上
    movl    %esi, -24(%rbp) ; 第2个参数 b (在 esi 中) → 栈上
    movl    -20(%rbp), %edx ; a 加载到 edx
    movl    -24(%rbp), %eax ; b 加载到 eax
    addl    %edx, %eax      ; eax = eax + edx  (真正的加法!)
    movl    %eax, -4(%rbp)  ; 结果 sum 存到栈上
    movl    -4(%rbp), %eax  ; sum 加载到 eax 准备返回
    popq    %rbp            ; 恢复调用者的栈基址
    ret                     ; 返回(返回值在 eax 中)
```

**关键观察**：
- `add` 函数需要 7 条指令才完成 `a + b`，大部分时间在**搬数据**
- 返回值约定通过 `%eax` 寄存器传递
- 这就是之前学的 **CPU 时钟周期**的作用——每条指令消耗若干个周期

### 2.3 动手：指令执行到底多快？

```bash
# 用 perf 看一个简单运算消耗了多少 CPU 周期
perf stat -e cycles,instructions,cache-misses dd if=/dev/zero of=/dev/null count=1000000 2>&1

# 输出示例:
#  1,234,567,890  cycles                    ← 消耗的时钟周期(之前学的 3.0GHz = 每秒 30 亿个)
#  3,456,789,012  instructions              ← 执行的指令条数
#       12,345    cache-misses              ← 缓存没命中次数
#
# IPC (Instructions Per Cycle) = instructions / cycles ≈ 2.8
# 说明平均每周期执行了 2.8 条指令(现代 CPU 超标量+流水线的效果)
```

### 2.4 指令周期——取指·译码·执行·写回

每条指令都经过这四个阶段（之前学过，现在用具体例子感受）：

```
addl %edx, %eax 这条指令的执行过程：

阶段1(取指): CPU 根据 RIP 寄存器(存着下一条指令地址)
            → 从 L1 指令缓存中读出 addl 的机器码 → 放入指令寄存器
阶段2(译码): 控制单元解析机器码
            → "哦, 这是一条加法指令, 源操作数是 edx, 目标操作数是 eax"
阶段3(执行): ALU(算术逻辑单元)做 32 位加法: edx 的值 + eax 的值
阶段4(写回): 结果写回到 eax 寄存器
```

```bash
# 直接看机器码和汇编的对应关系
gcc -c -O0 -o /tmp/cpu-demo.o /tmp/cpu-demo.c
objdump -d /tmp/cpu-demo.o | grep -A 10 '<add>:'
# 输出:
# 0000000000000000 <add>:
#    0:  55              push   %rbp        ← 55 是 push %rbp 的机器码(1字节!)
#    1:  48 89 e5        mov    %rsp,%rbp   ← 48 89 e5 是这条指令的机器码(3字节)
#    4:  89 7d ec        mov    %edi,-0x14(%rbp)
#    7:  89 75 e8        mov    %esi,-0x18(%rbp)
#    a:  8b 55 ec        mov    -0x14(%rbp),%edx
#    d:  8b 45 e8        mov    -0x18(%rbp),%eax
#   10:  01 d0           add    %edx,%eax   ← 01 d0 = addl %edx,%eax(2字节)
#   12:  89 45 fc        mov    %eax,-0x4(%rbp)
#   15:  8b 45 fc        mov    -0x4(%rbp),%eax
#   18:  5d              pop    %rbp
#   19:  c3              ret
```

**关键发现**：`push %rbp` 的机器码只有 **1 个字节**，而 `mov %rsp,%rbp` 有 **3 个字节**——指令是变长的（x86-64 特性）。

## 三、内存层次——为什么你的电脑不是直接用硬盘跑程序？

### 3.1 存储金字塔

```
                   容量         延迟(大概)      类比
                   ────        ─────────      ──────────
寄存器             几十字节      0.3 ns        手心里捏着的东西
L1 缓存            32 KB        1 ns          桌上的笔
L2 缓存            256 KB       4 ns          抽屉里的本子
L3 缓存            8~32 MB      12 ns         走到书架前
主存(RAM)          8~64 GB      100 ns        走到公司楼下取快递
SSD                256 GB~2 TB  100,000 ns    坐高铁去隔壁城市取
HDD                1~16 TB      10,000,000 ns 走路绕地球一圈
```

**核心原理**：CPU 越来越快，内存的访问速度远远跟不上。缓存（Cache）是解决这个问题的关键。

### 3.2 动手：感受各级存储的速度差距

```bash

# L1d cache: 32 KiB  ← 数据和指令分开的一级缓存(哈佛架构!)
# L1i cache: 32 KiB
# L2 cache:  256 KiB
# L3 cache:  16 MiB   ← 三级缓存是所有核共享的

# 2. 查看缓存块大小(决定一次从内存搬多少数据进缓存)
getconf LEVEL1_DCACHE_LINESIZE
# 64 ← 一次搬 64 字节(缓存行/cache line)

# 3. 用 sysbench 测试内存延迟
sysbench memory --memory-block-size=1K --memory-total-size=10G run 2>/dev/null | grep -E "transferred|Operations"
# 或更简单直观的方式：
# 访问顺序 vs 随机, 感受缓存的威力

# 4. 查看虚拟内存使用情况
vmstat 1 5
# si(swap in) 和 so(swap out) 不为零 → 物理内存不够, 在换页
# 一旦开始换页(swap), 系统会明显变慢——因为硬盘比内存慢 1000 倍
```

### 3.3 动手：写一个程序感受缓存命中 vs 缓存未命中的差距

```bash
cat > /tmp/cache-test.c << 'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define SIZE (64 * 1024 * 1024)  // 64 MB, 远超 L3 缓存, 确保缓存会miss
#define STRIDE 64                 // 64 字节, 正好是一个 cache line 大小

int main() {
    char *arr = (char*)malloc(SIZE);
    clock_t start, end;

    // 顺序访问 —— 缓存友好 (每次访问 stride=64, 正好每 cache line 命中一次)
    start = clock();
    for (int i = 0; i < SIZE; i += STRIDE) {
        arr[i]++;  // 每次+64, 正好跳到下一个 cache line 的第一个字节
    }
    end = clock();
    printf("顺序访问(stride=64, cache友好):  %.2f ms\n",
           1000.0 * (end - start) / CLOCKS_PER_SEC);

    // 随机跨步访问 —— 缓存不友好 (每次都跳到很远, 硬件预取失效)
    start = clock();
    volatile long sum = 0;
    for (int i = 0; i < SIZE / STRIDE; i++) {
        // 用简单的"伪随机"跳跃: 每次跳一个质数步长, 绕回
        int idx = (i * 7919) % (SIZE / STRIDE);
        arr[idx * STRIDE]++;
    }
    end = clock();
    printf("随机跳转(cache不友好):       %.2f ms\n",
           1000.0 * (end - start) / CLOCKS_PER_SEC);

    free(arr);
    return 0;
}
EOF

gcc -O0 -o /tmp/cache-test /tmp/cache-test.c && /tmp/cache-test
# 预期输出:
# 顺序访问(stride=64, cache友好):  ~15 ms   ← 快! 硬件预取器能预测, 提前把下一块搬进缓存
# 随机跳转(cache不友好):           ~80 ms   ← 慢5倍! 每次都跳到预想不到的位置, 只能等内存
```

### 3.4 深入解析：为什么顺序访问快？你关于"磁盘→内存→缓存"的疑问

**关键认知：这个测试完全不涉及磁盘。**

`malloc()` 分配出来的是**已经在 RAM 里的内存**，不是从磁盘读的。数据路径是：

```
你理解的路径（❌ 错误）：
  磁盘 → 主存(RAM) → CPU缓存(L1/L2/L3) → CPU寄存器
  ↑ 这是文件 I/O 的路径, 不适用于这个测试

这个测试的路径（✅ 正确）：
  RAM → L3缓存 → L2缓存 → L1缓存 → CPU寄存器
  ↑ 这就是 CPU 访问内存的路径, 全程在 RAM 里, 没有磁盘参与
```

#### 为什么 stride=64 比随机跳转快？

核心原因：**cache line 的预取机制（Prefetching）**。

```
cache line = 64 字节。
CPU 从 RAM 读取数据时, 不是一次读 1 个字节, 而是一次读 64 字节——一整条 cache line。

顺序访问(每次+64, 跳到下一个 cache line 的起点):
  arr[0]   → CPU 要读 arr[0], 把 arr[0~63] 整条 cache line 搬进 L1
  arr[64]  → 读 arr[64], 再次触发 cache line 搬运 arr[64~127]
  arr[128] → 读 arr[128], 搬运 arr[128~191]
  ...
  ↑ 硬件的"预取器"(Prefetcher)很快发现规律: "每次+64, 持续往前"
    于是提前预取下一批, 等 CPU 真正要用时, 数据已经在缓存里了
    这就叫"缓存友好"

随机跳转(每次都跳到完全不同的位置):
  arr[54321] → CPU 要读 arr[54321], 搬运 arr[54321~54384]
  arr[12345] → CPU 要读 arr[12345], 但 arr[12345] 不在缓存里!
               → 等 100ns 从 RAM 重新加载
  ...
  ↑ 预取器完全无法预测 "下一个位置在哪"
    每次都是 cache miss, 每次都要等慢 100 倍的内存
    这就叫"缓存不友好"
```

#### 用一张图感受

```
顺序访问（预取器提前加载）:
时间线 ──────────────────────────────────────→
CPU:   需要[0]      需要[64]      需要[128]     需要[192]
L1:    [0~63]已到！ [64~127]已到！[128~191]已到！[192~255]已到！
        ↑ 不等待       ↑ 不等待       ↑ 不等待       ↑ 不等待

随机访问（预取器歇菜）:
CPU:   需要[54321]   需要[12345]   需要[98765]   需要[43210]
L1:    [54321~]刚到  [12345~]不在！[98765~]不在！[43210~]不在！
        ↑ 等待100ns    ↑ 等待100ns    ↑ 等待100ns    ↑ 等待100ns
```

#### 为什么这个实验用 64MB？

因为 64MB 远超你的 L3 缓存（通常 8~32MB），确保数据不在 L3 里——每次访问都迫使 CPU 从 RAM 加载。这样才能放大"顺序 vs 随机"的差距。

### 3.5 深入：预取器和 CPU 是并行工作的

你刚才问了一个非常关键的问题：**是不是 CPU 在做其他操作时，硬件同时在后台把下一批数据搬进缓存？**

**答案是：是的。** 这就是预取器快的核心原因——CPU 和预取器**不在争抢同一个时间**，它们在不同"通道"上并行工作。

#### CPU 不只有执行单元，它还有预取单元

CPU 内部不止是"做算术的逻辑电路"。现代 CPU 有多个并行工作的**微架构单元**：

```
CPU 内部并行工作的单元（不同通道，互不干扰）：

┌─────────────────────────────────────────────────────┐
│                    微架构单元                         │
│                                                     │
│  核心0  核心1  核心2  核心3                           │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐                        │
│  │执行│ │执行│ │执行│ │执行│                        │
│  │单元│ │单元│ │单元│ │单元│  ← 做算术、比较、跳转    │
│  │ALU │ │ALU │ │ALU │ │ALU │                        │
│  └──┬─┘ └──┬─┘ └──┬─┘ └──┬─┘                        │
│     │      │      │      │                           │
│     └──────┼──────┼──────┘                           │
│            │      │                                  │
│      ┌─────┴──────┴─────┐                            │
│      │    前端单元        │                            │
│      │  ┌────────────┐  │                            │
│      │  │ 取指/译码   │  │  ← 把指令读进核心           │
│      │  └────────────┘  │                            │
│      │  ┌────────────┐  │                            │
│      │  │ 分支预测    │  │  ← 猜下一条指令去哪         │
│      │  └────────────┘  │                            │
│      │  ┌────────────┐  │                            │
│      │  │ 数据预取器  │  │  ← 预测下一个数据地址,       │
│      │  │ (Prefetch) │  │     提前发"加载"命令给内存    │
│      │  └────────────┘  │                            │
│      └──────────────────┘                            │
│                                                     │
│  关键: 预取器是一个独立的硬件单元,                     │
│        它和 ALU 不是同一个东西,                        │
│        它可以在 ALU 忙的时候独立工作!                  │
└─────────────────────────────────────────────────────┘
```

#### 并行工作的具体过程

```
时钟周期:    1      2      3      4      5      6      7      8
            ───    ───    ───    ───    ───    ───    ───    ───

ALU (做算术):
            读arr[0] 读取值    做加法    写回arr[0]   读arr[64] 读取值
            ↑ 加载           ↑ 加法运算 ↑ 写回        ↑ 加载...   ↑ 加法...
            (3个周期)        (1个周期)   (1个周期)    (3个周期)   (1个周期)

预取器 (独立工作, 不同时间槽):
            ───       发现规律"stride=64"
                  ↓    发加载命令给内存
                  ↓    [64~127] 从 RAM → L3
                  ↓    [64~127] 从 L3 → L2
                  ↓    [64~127] 从 L2 → L1
                        [64~127] 已在缓存中 ✅
                        等 ALU 要 arr[64] 时 → 立即取, 不用等!
```

#### 类比：厨房里的"流水线 + 并行"

```
做饭的场景：

厨师(= ALU)：切菜 → 炒 → 装盘 → 切下一道菜
                ↑ 这是主通道，厨师在忙

助手(= 预取器)：
                厨师在炒菜的同时，助手把下一道菜的食材提前备好了
                厨师炒完第一道菜的间隙，助手已经：
                  - 把锅洗干净了（预取下一块 cache line）
                  - 把第二道菜的配料切好了
                厨师炒完第一道菜，立刻开始炒第二道——不等待
```

#### 为什么随机访问做不到这一点？

```
ALU:  需要 arr[54321] 需要 arr[12345] 需要 arr[98765]
         ↑                  ↑              ↑
预取器:  "下一个位置在哪？不知道！"
         → 预取器只能盲目猜测
         → 猜错了浪费带宽
         → 猜对了运气
         → 所以干脆不猜
         → ALU 只能等 100ns 去 RAM 取
```

**关键点**：预取器不是"等 CPU 空闲了才工作"，它是**和 CPU 同时工作**的独立硬件——只是它能预测成功的前提是"有规律可循"。

## 四、流水线（Pipeline）——CPU 为什么能同时做多件事

### 4.1 理论

```
经典五级流水线:

时钟周期:   1       2       3       4       5       6       7
          ────    ────    ────    ────    ────    ────    ────
指令1:    取指 → 译码 → 执行 → 访存 → 写回
指令2:           取指 → 译码 → 执行 → 访存 → 写回
指令3:                  取指 → 译码 → 执行 → 访存 → 写回
指令4:                         取指 → 译码 → 执行 → 访存 → 写回
                          ↑
                    每个周期都有5条指令在不同阶段!
                    就像工厂流水线, 不是做完一个再做下一个
```

**没有流水线**：5 条指令需要 25 个周期（每条 5 周期）
**有流水线**：5 条指令只需要 9 个周期（4 个周期填满流水线 + 5 条指令）

### 4.2 动手：现代 CPU 的流水线有多深？

## 五、中断（Interrupt）——CPU 怎么知道键盘被按了？

### 5.1 理论

CPU 不能无时无刻去查看键盘有没有输入（太浪费周期），而是靠**中断机制**：键盘被按时 → 硬件发送中断信号 → CPU 暂停当前工作 → 执行中断处理程序 → 恢复原工作。

```
正常执行:  指令1 → 指令2 → 指令3 → 指令4 → ...
                            ↑
中断发生:  指令1 → 指令2 → 中断信号到了! → 保存现场 → 执行中断处理 → 恢复现场 → 指令3 → ...
```

## 六、操作系统怎么加载程序——从 ELF 到进程

### 6.1 理论

可执行文件不是纯机器码，而是按照 **ELF 格式**组织的，包含代码段(.text)、数据段(.data)、符号表等。

**操作系统加载一个程序的步骤**：
```
1. 解析 ELF 头 → 找到各段的地址和大小
2. 分配虚拟地址空间(页表映射)
3. 加载 .text (代码) 和 .data (数据) 到内存
4. 动态链接: 加载 .so 共享库(如 libc)
5. 设置栈(命令行参数和环境变量放在这里)
6. 跳转到 _start → 最终调用 main()
```

## 七、虚拟内存——每个程序都以为自己有整个内存

### 7.1 理论

每个进程看到的地址都是**假的**——虚拟地址。CPU 内置的 **MMU（内存管理单元）** 通过**页表**把虚拟地址翻译成物理地址。

```
程序看到的:                    物理内存实际:
0x00007fff12345678  ──MMU──→  0x00000008abcdef00

每个进程都有独立的页表(进程隔离!)
多个进程的同一个虚拟地址映射到不同的物理地址

好处:
1. 隔离: 程序A不能读写程序B的内存
2. 扩大: 可以用比物理内存更大的地址空间(swap到硬盘)
3. 共享: 多个进程的 .text 可以映射到同一物理页(libc.so 只存一份!)
```

### 7.15 深入：页表是如何工作的——地址翻译的全过程

> **前置知识**：之前说过，虚拟地址通过 MMU 翻译成物理地址，中间靠"页表"。但页表到底是什么？地址是怎么翻译的？内核怎么知道哪些虚拟地址要映射到哪里？

#### 7.15.1 概念总览：先记三个核心结论

**结论一：任何虚拟地址 = 页号 + 页内偏移**

```
虚拟地址不是一条直线，而是分成两段:
  页号（高36位） + 页内偏移（低12位）

  0x00007FAB1234  →  页号=0x00007FAB1, 偏移=0x234
                     ↑ 查页表用的      ↑ 在一页内找哪个字节
```

**结论二：页 = 4KB 数据块（装数据的容器）**

```
页就是内存中 4096 个连续字节，里面放什么由程序决定:
  'A' 'B' 'C' '\0'  |  int 42  |  float 1.25  |  机器指令
  字符               |  整数     |  浮点数      |  代码
```

**结论三：页表 = 目录（告诉你页号对应的物理地址在哪）**

```
页号 0 → 物理帧 300
页号 1 → 物理帧 1024   ← 查完页表就知道"这页的数据实际在物理内存的哪个位置"
页号 2 → 物理帧 512
```

**一句话：**

```
页表是目录，页是数据。
目录告诉你"页号 1 的数据在物理地址 0x400000~0x400FFF"，
你去那里取偏移 0x100 的字节。
```

#### 7.15.2 页——4KB 数据块（纯粹讲"数据"是什么）

**页就是内存中一块连续的 4096 个字节。** 一个字节 = 8 位。这就是全部。

```
一个页（4096 字节）= 4096 个字节排成一排:
┌── 字节0 ──┬── 字节1 ──┬── ... ──┬── 字节4095 ──┐
│  8 bits   │  8 bits   │          │    8 bits   │
└───────────┴───────────┴──────────┴─────────────┘
```

**页里的 4096 个字节放什么？OS 不管，程序决定。**

字节本身就是 8 位的容器，里面塞什么数据类型取决于你怎么用这块内存——字符、整数、浮点数、机器指令都可以，甚至可以混放：

```
同一个 4KB 页的内容（举例）:

┌─ 0x1000 ┐ 'A' 'B' 'C' '\0'      ← 一个 C 字符串的前 4 字节
├─ 0x1004 ┤ 0x2A 0x00 0x00 0x00   ← int x = 42（小端序，占 4 字节）
├─ 0x1008 ┤ 0x3F 84 00 00 ...     ← float y ≈ 1.25（IEEE 754，占 4 字节）
├─ 0x1010 ┤ 0x89 05 0x85 C0       ← 两条 x86 机器指令
├─ 0x1014 ┤ ...                   ← 剩下的 3000+ 字节可能没用
└─ 0x1FFF ┘                       ← 第 4095 个字节

注意: 同一个页里同时放了字符、整数、浮点数、指令——对 OS 来说它们就是一串字节
```

**"寻址"到底是什么操作？**

寻址 = 从这 4096 个字节里**精准定位某一个字节**，然后对它做操作。

```
偏移 0x000 = 第 0 个字节（页的起始位置）
偏移 0x001 = 第 1 个字节
偏移 0x100 = 第 256 个字节
偏移 0xFFF = 第 4095 个字节（页的最后一个字节）
```

寻址成功后做三件事之一：

```
1. 读 (load):    把这个字节的 8 位值读到寄存器
2. 写 (store):   把一个值写进这个字节
3. 执行 (fetch): 把这个字节当机器码执行（CPU 从代码段读）
```

一个具体例子——`int x = 42;` 是怎么对应到页里的字节：

```
int x = 42;

假设编译器把 x 放在某个页的偏移 0x004 处:
  页号 | 偏移
  页号 | 0x004

写入时: CPU 写 4 字节 0x2A 0x00 0x00 0x00 到 偏移0x004~0x007
读取时: CPU 从 偏移0x004 读回 0x2A 0x00 0x00 0x00，即十进制 42
```

#### 7.15.3 虚拟地址的结构——页号占几位？偏移占几位？

**纯纯的地址拆分，不讲数据内容。**

一个虚拟地址由两部分拼成：**页号**（告诉 MMU 去查哪一页）+ **页内偏移**（告诉 MMU 那一页的哪个字节）。

```
页大小 = 4KB = 2^12 字节
→ 需要 12 位来区分页内 4096 个字节中的某一个
→ 所以页内偏移 = 12 位

对于 x86-64（实际用 48 位地址空间）:
  页号 = 48 - 12 = 36 位
  偏移 = 12 位

48 位虚拟地址:
  47                   36    12    0
  │←──── 36 位页号 ──→│←12 位偏移→│
```

**逐位拆解一个真实地址**:

```
虚拟地址: 0x00007FAB1234
十六进制展开(每4位一组):
  0    0    0    0    7    F    A    B    1    2    3    4
  0000 0000 0000 0000 0111 1111 1010 1011 0001 0010 0011 0100
  ────────────────┬────────────────┬──────┬──────┬──────
                 │                │      │      │
                 36 位页号部分      12 位偏移部分
                    0x00007FAB1      0x234

页号 = 0x00007FAB1
偏移 = 0x234 = 564（在 0~4095 范围内，正确 ✅）
```

#### 7.15.4 页表的本质——一张大查找表

把页表看成一张"翻译字典"：

```
页号 (输入)  →  查页表  →  帧号 (输出)

页表项结构 (每个项 8 字节):
  ┌── 47 位 ───┬─── 5 位 ───┐
  │ 物理帧号   │  标志位    │
  │            │ V A D U/S ...│
  └────────────┴────────────┘
  帧号(47位)  有效/脏/读写/用户/全局...
```

**标志位详解**（x86-64 PTE 标志位字段）：

| 位 | 标志 | 含义 |
|----|------|------|
| V  | Valid | 页表项有效。0=这一页还没分配物理内存（缺页中断） |
| R/W| 读写 | 0=只读，1=可读可写 |
| U/S| 用户/内核 | 0=只允许内核访问，1=用户程序也可访问 |
| P | Present | 同 Valid 的早期名称 |
| A | Accessed | 这页被访问过了（用于换页时判断哪些页可以换出） |
| D | Dirty   | 这页被写入过了（用于换页时判断是否需要写回磁盘） |

**页表的工作流程**（MMU 硬件执行）：

```
1. CPU 发出虚拟地址 VA
2. MMU 用 VA 的 12 位页内偏移直接保留下来（不做翻译）
3. MMU 用 VA 的 36 位页号作为索引 → 去页表中查
4. 找到对应页表项 → 取出 47 位物理帧号 PFN
5. 检查 V 标志位：
   - V=1 → 有效，拼接 PFN(47位) + 偏移(12位) = 物理地址 PA
   - V=0 → 无效，触发缺页中断
6. 检查 R/W 标志位：
   - 写操作 + R/W=0 → 触发段错误(segmentation fault)
   - 写操作 + R/W=1 → 允许写入，同时置 D(脏) 位
7. 用物理地址 PA 访问内存
```

#### 7.15.5 多级页表——为什么不能只用一张大表？

**为什么单级页表不行？**

```
如果只用一张大表（36 位页号）:
  表项数 = 2^36 = 68,719,476,736 项 ≈ 680 亿项
  每项 8 字节 → 680 亿 × 8 = 5,497,558,138,880 字节 ≈ 5.2 TB!

  → 你的物理内存只有 32GB，存不下 5.2TB 的页表
  → 而且 99% 的页号根本没用到，表项全是空的，浪费！
```

**解决方案：多级页表（稀疏分配）**

把大表拆成多级，每级 4KB（正好一页），只有用到了才分配：

```
x86-64 四级页表结构:

虚拟地址 48 位位结构（从高到低）:
  47        39    30    21    12    0
  │←  9 位  →│←  9 位  →│←  9 位  →│←  9 位  →│

  P4 索引     P3 索引     P2 索引     P1 索引     页内偏移(12位)

  ┌───────────┬───────────┬───────────┬───────────┐
  │   P4T     │   P3T     │   P2T     │   P1T     │
  │ 表目录     │ 表目录     │ 表目录     │ 叶子页表   │
  │ 4KB(512项) │ 4KB(512项) │ 4KB(512项) │ 4KB(512项) │
  │ CR3 指向   │ P4T指向   │ P3T指向   │ P2T指向   │
  └────┬──────┴────┬──────┴────┬──────┴────┬──────┘
       │           │           │           │
       9位索引     9位索引     9位索引     9位索引
```

**每级的含义**：

```
  P4T[0~511]   → 每个表项指向一个 P3T（或者有效位=0，表示这片区域没用）
  P3T[0~511]   → 每个表项指向一个 P2T
  P2T[0~511]   → 每个表项指向一个 P1T
  P1T[0~511]   → 每个表项指向一个物理帧（叶子层，真正存帧号的地方）

  最多 512^4 × 4KB = 2^48 = 256 TB（刚好覆盖 x86-64 的 48 位地址空间）
	  怎么算的: 512^4 = (2^9)^4 = 2^36, 2^36 × 4KB = 2^36 × 2^12 = 2^48
  但大部分项是空的 → 只有用到的区域才分配页表
```

**地址翻译的完整算法**（MMU 硬件执行，每步一个内存读取）：

```
输入: 虚拟地址 VA = 48 位

步骤 1: 从 CR3 寄存器读取 P4T 的物理地址
  P4T_base = CR3 寄存器内容（指向 P4T 的物理帧首地址）

步骤 2: 用 P4 索引(9位) 访问 P4T
  P4_index = (VA >> 39) & 0x1FF     // 右移39位, 取低9位
  P3T物理地址 = P4T[P4T_base + P4_index × 8]

步骤 3: 用 P3 索引(9位) 访问 P3T
  P3_index = (VA >> 30) & 0x1FF
  P2T物理地址 = P3T[P3T_base + P3_index × 8]

步骤 4: 用 P2 索引(9位) 访问 P2T
  P2_index = (VA >> 21) & 0x1FF
  P1T物理地址 = P2T[P2T_base + P2_index × 8]

步骤 5: 用 P1 索引(9位) 访问 P1T（叶子层）
  P1_index = (VA >> 12) & 0x1FF
  PTE内容 = P1T[P1T_base + P1_index × 8]

步骤 6: 从 PTE 中提取信息
  有效位 V   = PTE[0]
  物理帧号 PFN = PTE[52:12]（中间 40 位，因为高 16 位是零扩展的）
  权限 RW    = PTE[1]

步骤 7: 检查标志位
  if V == 0:  触发缺页中断
  if 写操作 && RW == 0:  触发段错误

步骤 8: 拼接物理地址
  偏移 offset = VA & 0xFFF    // 取低 12 位
  物理地址 PA = (PFN << 12) | offset
  即: PA = PFN × 4KB + offset
```

**用一个具体数字走一遍**：

```
虚拟地址 VA = 0x00007FFF5678

二进制展开（48 位，每 9 位一组对应一级索引，低 12 位是偏移）:

  47    41    32    23    14    11    0
  │      │      │      │      │     │
  │←9位→│←9位→│←9位→│←9位→│←12位→│
  000000000 000000000 111111111 111110101 011001111000
  └───────┘ └───────┘ └───────┘ └───────┘ └──────────
    P4=0     P3=0     P2=0x1FF  P1=0x17D  偏移=0x678

  从右往左看:
    偏移(12位) = 0110 0111 1000 = 0x678  ← 页内第 1656 个字节
    P1 索引(9位) = 101 1111 101 = 0x17D = 381  ← P1T 的第 381 项
    P2 索引(9位) = 111 1111 111 = 0x1FF = 511  ← P2T 的第 511 项
    P3 索引(9位) = 000 0000 000 = 0     ← P3T 的第 0 项
    P4 索引(9位) = 000 0000 000 = 0     ← P4T 的第 0 项

逐级查表:
  P4T[0]    → P3T_base = 0x12A30000
  P3T[0]    → P2T_base = 0x2B100000
  P2T[511]  → P1T_base = 0x3C200000
  P1T[381]  → PTE = {PFN=0x4D5E, V=1, RW=1}

  物理地址 = PFN × 4KB + 偏移
          = 0x4D5E << 12 | 0x678
          = 0x4D5E0000 + 0x678
          = 0x4D5E0678
```

**对比：单级页表 vs 多级页表（内存开销）**：

```
假设进程只用了 1MB 的虚拟地址空间（256 页，且地址是连续的）

单级页表:
  需要 2^36 项 × 8 字节 = 5.2 TB（无论用多少，都要全部分配）
  实际只用了 256 页 → 浪费了 5.2TB

多级页表:
  先算需要多少张叶子页表（P1T）:
    1 张 P1T = 512 项 × 8 字节 = 4KB
    1 张 P1T 覆盖 512 × 4KB = 2MB 地址空间
    1MB < 2MB → 只需要 1 张 P1T！

  再算上层页表:
    1 张 P2T 覆盖 512 × 2MB = 1GB → 1 个 P2T 项就够了
    1 张 P3T 覆盖 512 × 1GB = 512GB → 1 个 P3T 项就够了
    1 张 P4T 覆盖 512 × 512GB = 256TB → 1 个 P4T 项就够了

  但即使只用 1 项，P2T/P3T/P4T 本身也是 4KB 整张表:
    P4T(4KB) + P3T(4KB) + P2T(4KB) + P1T(4KB) = 16 KB
  只分配了用到的 4 张表，其余 2^32 张表都不分配
  节省了 5.2TB - 16KB ≈ 5.2TB
```

#### 7.15.6 地址翻译的完整过程——一个地址的旅程

以 `x = 3.14` 这样的指令为例，看虚拟地址 `0x00007FFF5678` 怎么变成物理地址：

```
指令:  mov float_value, 0x00007FFF5678

步骤1: CPU 发出虚拟地址
        48 位地址:  00000000 0000 0000 0111 1111 1111 1111 1010 110 0111 0000 1111 1000 0111 1000
        分解:      P4=0x000 P3=0x003 P2=0x1FF P1=0x07E  偏移=0x878

步骤2: CR3 寄存器中存着 P4T 的物理地址
        CR3 → 物理地址 0x12345000（就是 P4T 在物理内存中的位置）

步骤3: 查 P4T[0x000]
        读 P4T 第 0x000 项
        得到: 有效位=1, P3T 物理地址 = 0x12A30000

步骤4: 查 P3T[0x003]
        读 P3T 第 0x003 项
        得到: 有效位=1, P2T 物理地址 = 0x2B100000

步骤5: 查 P2T[0x1FF]
        读 P2T 第 0x1FF 项
        得到: 有效位=1, P1T 物理地址 = 0x3C200000

步骤6: 查 P1T[0x07E]（叶子层）
        读 P1T 第 0x07E 项
        得到: 有效位=1, 物理帧号 = 0x4D5E, 权限=RW

步骤7: 拼接物理地址
        物理帧号 0x4D5E × 4KB = 0x4D5E0000
        加偏移 0x878
        物理地址 = 0x4D5E0878

步骤8: 检查权限
        RW + 读操作 → 允许 ✅
        如果试图写入但权限是 RO → 触发段错误(segmentation fault)!

步骤9: 从物理地址 0x4D5E0878 读 4 字节数据

整个过程由 MMU 硬件自动完成, CPU 不需要"停"下来
翻译耗时: 约 1-3 个时钟周期 (有 TLB 缓存时)
         约 100+ 个时钟周期 (TLB miss, 需要查多级页表)
```

#### 7.15.7 TLB——页表翻译的缓存

每次地址访问都要查 4 级页表（4 次内存读取），太慢了。所以 CPU 内置了一个 **TLB（Translation Lookaside Buffer）**，相当于页表的 L1 缓存：

```
地址翻译过程（有 TLB）：

CPU 发虚拟地址
    ↓
查 TLB ──→ 命中？ → 直接得到物理地址（1 个时钟周期！）
    │
    ↓ 未命中
查多级页表（100+ 个时钟周期）
    ↓
把结果写回 TLB
    ↓
用物理地址访问内存
```

```bash
# 查看 TLB 的命中/未命中统计
cat /proc/cpuinfo | grep tlbsize
# or
lscpu | grep -i "tlb"
# L1d TLB: 1024 4K, 32 2M    ← L1数据缓存对应的TLB大小
# L1i TLB: 1024 4K, 32 2M    ← L1指令缓存对应的TLB大小
# L2 TLB:  1024 4K, 4K 4M    ← L2缓存对应的TLB

# 用 perf 统计 TLB 未命中
perf stat -e dTLB-load-misses,dTLB-store-misses \
  dd if=/dev/zero of=/dev/null count=1000000 2>&1
```

#### 7.15.8 内核怎么为进程分配虚拟地址空间

当你 `execve()` 一个程序时，内核做这几步：

```
1. 创建进程内核数据结构（task_struct）
2. 分配一个新的 mm_struct（内存描述符）
3. 为 mm_struct 分配 P4T 页表（4KB 内存）
4. 初始化虚拟地址布局（按下面的模板）
5. 把 CR3 寄存器设置为新 P4T 的物理地址
6. 加载 .text/.data → 分配物理帧 + 写页表
7. 分配栈 → 分配物理帧 + 写页表
8. 跳转到 _start 执行
```

**64 位 Linux 虚拟地址空间布局**：

```
高地址 ←────────────────────────────────────── 低地址
┌────────────────────────────────────┐  0x00007FFFFFFFFFFF
│ 栈 (向下增长)                       │
│  ~16GB 栈空间                       │
├────────────────────────────────────┤  0x00007FFFFFFF0000
│ mmap 区 (动态库, 共享内存, mmap)     │
│  libc.so, libpthread.so ...          │
├────────────────────────────────────┤  0x00007F...
│ BRK/HEAP (向上增长)                  │
│ malloc 从这里分配                     │
├────────────────────────────────────┤  0x0000000000000000
│ ⚠️ 空洞区域: 0x00007FFF00000000     │
│   故意空出来, 防止栈和堆碰在一起       │
├────────────────────────────────────┤  0x00007FFF00000000
│ .text (代码)                        │
│ .data (全局变量)                    │
│ .bss (未初始化全局变量)              │
├────────────────────────────────────┤  0x0000000000001000
│ 内核预留 (user space 用不了)          │
│  0x0000000000000000~0x0000000000000FFF│
└────────────────────────────────────┘  0x0000000000000000
```

#### 7.15.10 缺页中断——写的时候才真正分配内存

一个反直觉的事实：**`malloc()` 分配内存时，并不真的分配物理内存！**

```bash
# 写一个"假装分配了100MB，但实际上只用了4KB"的程序
cat > /tmp/alloc-test.c << 'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main() {
    // malloc 100MB
    char *p = malloc(100 * 1024 * 1024);
    printf("malloc 后 RSS: 见 /proc\n");

    // 什么都不写 → 没有真正分配物理内存!
    // 系统调用 brk() 只是扩大了"可用虚拟地址范围"
    // 页表里没有映射 → 访问时会触发缺页中断

    system("cat /proc/self/status | grep VmRSS");
    // VmRSS 不会涨到 100MB

    // 写入数据 → 触发缺页中断, 内核才真正分配物理页
    memset(p, 0, 100 * 1024 * 1024);
    printf("memset 后 RSS: 见 /proc\n");

    system("cat /proc/self/status | grep VmRSS");
    // VmRSS 现在约等于 100MB
}
EOF

gcc -o /tmp/alloc-test /tmp/alloc-test.c
/tmp/alloc-test
# 预期输出:
# malloc 后 RSS: 见 /proc
# VmRSS:    2000 kB         ← 只有几 MB, 没有真分配
# memset 后 RSS: 见 /proc
# VmRSS:  102400 kB         ← 现在才真的分配了
```

**缺页中断的工作流程**：

```
进程访问虚拟地址 → MMU 查 TLB → miss → 查多级页表
    ↓
页表项有效位 = 0（这页还没分配物理内存!）
    ↓
触发"缺页中断"(Page Fault, 不是错误! 是通知内核)
    ↓
内核缺页处理函数:
    1. 检查这个地址是否合法（在进程已分配的区域内）
    2. 检查是否有足够空闲物理页
    3. 如果内存不够 → 换页(把不常用的页换到 swap)
    4. 分配一个空闲物理页
    5. 把页表项写为: 有效=1, 帧号=新分配的, 权限=RW
    6. 刷新 TLB
    7. 让进程重新执行那条指令
    ↓
MMU 查 TLB → 命中! → 翻译成功 → 进程继续
```

## 八、总线（Bus）——数据在部件之间怎么传输

### 8.1 理论

```
CPU ←→ 内存 ←→ 硬盘 ←→ 外设(键盘/网卡/GPU)

这些部件通过"总线"连接。现代计算机有三条主要总线:
  数据总线: 传输实际数据(双向, 64位并排)
  地址总线: 传输地址(单向, CPU → 其他部件)
  控制总线: 传输控制信号(读/写/中断等)

之前学的"64位CPU"说的就是数据总线的宽度。
```

## 九、CPU 的工作原理总结：一段完整的数据之旅

把上面所有章节串起来，看一个完整的 `x = a + b` 从开始到结束经历了什么：

```
1. 键盘输入 → 键盘控制器发出中断(第五节)
            → CPU 响应中断，通过总线(第八节) 读取按键码

2. 操作系统把程序从硬盘加载到内存(第六节 ELF)
            → SSD → SATA/PCIe 总线 → RAM

3. CPU 开始执行(第二节):
   a. 取指: 从内存取机器码 8b 45 ec (mov -0x14(%rbp),%edx)
           → 通过地址总线发出地址 → 通过数据总线读取数据
           → 先查 L1 指令缓存(第三节)
           → 缓存没有 → L2 → L3 → 内存(越来越慢)
   b. 译码: 控制单元解析 8b 45 ec → "哦, mov 指令, 从栈上加载"
   c. 执行: ALU 计算有效地址(基址 + 偏移)
   d. 写回: 数据写入 edx 寄存器

4. 流水线(第四节)让步骤 1-4 同时进行(下一条指令已经在取指了)

5. MMU(第七节)在每次内存访问时自动翻译虚拟地址 → 物理地址

6. 整个过程 0.x 纳秒就完成了, 因为程序在 L1 缓存里
```

```bash
# 用一个命令看到整个数据之旅的统计
perf stat -e cycles,instructions,cache-references,cache-misses,\
  branches,branch-misses,page-faults,context-switches,migrations \
  ls -R /usr/share/doc/ > /dev/null 2>&1

# 输出解读:
# cycles:              总时钟周期数 — 衡量"花了多少时间"
# instructions:        执行了多少条指令
# IPC = instructions/cycles — 每周期指令数, 越大越好(>1 说明超标量/流水线有效)
# cache-references:    访问缓存的次数
# cache-misses:        缓存未命中次数(越高越慢!)
# branches:            分支指令数(if/for/while)
# branch-misses:       分支预测失败次数(流水线清空!)
# page-faults:         缺页中断次数(访问了不在物理内存的地址)
# context-switches:    进程切换次数
# migrations:          CPU 核心间迁移次数(跨核缓存同步有开销)
```
