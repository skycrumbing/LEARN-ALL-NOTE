# Netty 架构全景

## 一、为什么需要 Netty？

### 手写 NIO 服务器的痛点

用原生 NIO 写一个 TCP 服务器，你会遇到这些坑：

| 问题 | 说明 | 手写多痛苦 |
|------|------|-----------|
| **心跳机制** | 检测死连接 | 自己写定时器 + 读写超时 |
| **空闲检测** | 多久没数据就断连 | 自己维护时间戳 |
| **优雅关闭** | 关闭时不丢数据 | 自己处理半关闭状态 |
| **粘包/拆包** | TCP 是流式协议 | 自己写协议解码器 |
| **半包读写** | 数据分多次到达 | 自己拼包 |
| **零拷贝** | 减少内存复制 | 手写 `transferTo` |
| **内存泄漏** | DirectBuffer 手动释放 | `Unsafe` 操作易出错 |
| **线程模型** | EventLoop 分配策略 | 自己实现轮询/粘性分配 |
| **SSL/TLS** | 加密传输 | 自己接 JDK SSL |
| **连接风暴** | 瞬间大量连接 | 自己限流/丢弃策略 |
| **内存池** | 减少 GC 压力 | 自己实现 Slab 分配 |
| **Bug 修复** | 各种边缘 case | 花了数年的成熟框架 |

> **结论**：手写 NIO 服务器 = 重新发明轮子。Netty 把这些问题全部解决了。

### 手写 NIO 有多难？

```java
// 手写一个"完整"的 NIO 服务器至少需要：
// 1. Selector 主循环        → 200 行
// 2. 连接管理               → 100 行
// 3. 读写缓冲管理            → 150 行
// 4. 心跳检测               → 80 行
// 5. 空闲断连               → 80 行
// 6. 粘包拆包               → 200 行
// 7. 线程池管理             → 100 行
// 8. 优雅关闭               → 100 行
// 9. SSL 支持               → 150 行
// ...
// 总计：1000+ 行，且满是 bug
```

Netty 把这些封装成几十行配置：

```java
ServerBootstrap bootstrap = new ServerBootstrap();
bootstrap.group(boss, worker)
    .channel(NioServerSocketChannel.class)
    .childHandler(new ChannelInitializer<SocketChannel>() {
        @Override
        protected void initChannel(SocketChannel ch) {
            ch.pipeline().addLast(new MyHandler());
        }
    });
bootstrap.bind(8080).sync();
```

## 二、Netty 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    用户业务层                              │
│                                                         │
│   ChannelHandler (你写的业务逻辑)                         │
│   ├─ 编解码器 (Codec)                                    │
│   ├─ 日志/SSL/心跳                                       │
│   └─ 你的 Handler                                        │
├─────────────────────────────────────────────────────────┤
│                    Netty 核心层                            │
│                                                         │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐            │
│   │ Pipeline │─►│ ByteBuf  │─►│ EventLoop│            │
│   │ 责任链    │  │  内存管理 │  │  线程模型 │            │
│   └──────────┘  └──────────┘  └──────────┘            │
│                                                         │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐            │
│   │ Transport│  │  Channel  │  │ Bootstrap│            │
│   │ 传输层    │  │  通道抽象 │  │  启动配置 │            │
│   └──────────┘  └──────────┘  └──────────┘            │
├─────────────────────────────────────────────────────────┤
│                    IO 抽象层                              │
│                                                         │
│   NIO / AIO / 本地传输 / 嵌入式                          │
│   (Netty 屏蔽了底层 IO 差异，统一 API)                   │
└─────────────────────────────────────────────────────────┘
```

## 三、Netty 核心组件一览

| 组件 | 作用 | 对应 NIO |
|------|------|----------|
| `Bootstrap` | 启动引导，配置服务器 | — |
| `Channel` | 网络连接的抽象 | `Channel` |
| `EventLoop` | IO 事件处理线程 | Selector 主循环 |
| `EventLoopGroup` | EventLoop 线程池 | 线程池 |
| `ChannelHandler` | 业务处理器 | — |
| `ChannelPipeline` | Handler 责任链 | — |
| `ByteBuf` | 缓冲区 | `ByteBuffer` |
| `ChannelFuture` | 异步操作结果 | — |
| `ChannelOption` | 通道配置 | `setsockopt` |

## 五、从 IO 到 Netty 的飞跃

```
BIO 服务器:
  线程数 = 连接数

手写 NIO 服务器:
  线程数 = 1~N，但要自己处理一堆坑

Netty 服务器:
  线程数 = 1~N，自动处理所有坑
  你只需要关注业务逻辑
```

> **Netty 的本质**：一个基于 NIO 的高性能网络框架，
> 把 IO 细节全部封装，让你只写 `ChannelHandler` 处理业务。
